# 蓝牙钥匙（BLE iBeacon 广播）使用文档

> 面向使用者。功能怎么用看本文；为什么这么设计、踩过哪些坑见
> [`docs/research/ble-key-broadcast.md`](../research/ble-key-broadcast.md)。
> 版本：v0.3.003 起可用。入口：**设置 → 连接 → 蓝牙钥匙**。

---

## 一、这是什么

让手机变成一把「靠近就通电」的车钥匙。

手机持续广播一条 iBeacon 信号；车上的 ESP32（`espAutoUnlock` 项目）扫到这个信号、且信号足够强，
就判定「钥匙在旁边」→ 接通继电器给车通电。人走远、信号消失约 **75 秒**后自动断电。

**一句话**：手机在，车能发动；手机走了，车自动断电。

### 它防什么、不防什么

| 能 | 不能 |
|---|---|
| 防「忘拔钥匙 / 误启动」——人离开自动断电 | **不防盗**：iBeacon 广播是公开的，任何人拿到你的 32 位 UUID 都能播出一模一样的信号 |
| 手机在身上就能用车，不用掏 | 不能防「有人故意复制你的 UUID」 |
| 后台、锁屏、被杀进程都继续播 | 不能替代机械锁/报警器 |

> **务必知悉**：UUID 就是钥匙本体，没有防伪。真要防盗得改成 BLE 连接 + 挑战应答，
> 对端 ESP32 要重写，当前不做。

## 二、原理（30 秒看懂）

```
手机 ──广播 iBeacon（UUID = 固定前缀 + 2 位编号）──▶ ESP32 ──信号够强──▶ 通电
                                                    └──信号消失 15 秒──▶ 判「远」
                                                        再等 60 秒 ──▶ 断电
```

- 手机是**广播方**（peripheral），只发不收；
- ESP32 是**扫描方**（central），它测信号强度、它判近远、它控继电器。
  **判定权完全在车上，手机不知道对面认没认出来**（所以有个「自检」按钮，但它只在能扫到自己时
  给出强证据——多数机型扫不到自己，属正常，见第七节）。
- 手机不参与判定，所以**改阈值、标定信号都在对端做**（见第五节）。

## 三、手机侧怎么开（四步）

1. 手机连网 → 打开 App → **检查更新** → 装到 **0.3.003 或更高**
2. **设置 → 连接 → 拉到底 → 蓝牙钥匙** → 点进详情页
3. **填编号**（`00`~`99`）→ 打开「启用广播」开关
4. 状态变成 **广播中 · 快速（250ms）** → 通知栏出现「钥匙 NN · 广播中」

### 编号怎么选

| 规则 | 说明 |
|---|---|
| 每台手机一个号 | **两台手机填同一个号 = 同一把钥匙**，对端分辨不出，一台被删另一台也失效 |
| 首次必须手填 | 初始为空，不填不让开（防止两台新机默认都变 `01`） |
| 改号 = 换钥匙 | 编号决定 UUID 末两位，改完对端必须重新登记 |
| 建议带上编号改设备名 | 详情页「按编号改名」→ `OPPOReno9-03`，对端列表里好认 |

### 完整 UUID 在哪看

详情页「标识（对端登记用）」：32 位 hex（复制给对端用）+ 带连字符形式（nRF Connect 比对用）。
默认前缀 `627269646765000000000000000000`，编号 `03` → `62726964676500000000000000000003`。

## 四、对端怎么登记（ESP32 侧）

> 完整流程与坑见 [`espauto-unlock-change-request.md`](../research/espauto-unlock-change-request.md)
> 与设计文档 §14。这里只给「能跑通」的最短路径。

### 推荐：用 Qt 工具（UUID 不会打错，但名字要自己看一眼）

1. ESP32 接电脑串口 → 上电后 **10 秒内**发 `CONFIG` 进配置模式
2. 点 `SCAN` → 10 秒后出设备列表
3. 在列表里找 **UUID 列 = 你手机上那串 32 位**的那一行 → 选中 → 点「设为钥匙」
4. 工具会拼好命令并登记，名字默认用手机广播的名字

> ⚠ **登记前先确认名字里没有空格。** 手机广播的就是系统蓝牙名，而 `OPPO Reno9`、
> `HUAWEI Mate 40`、`Redmi Note 12` 这类出厂名**都带空格**。工具会把名字原样拼进命令，
> 空格一多，后面的地址和 UUID 就整体错位——**登记看起来成功，实际永远不通电**，且不报错。
>
> **最省事的做法**：先在 App 详情页「设备名 → 按编号改名」，它会去掉空格并加后缀
> （`OPPOReno9-03`）；改完再 `SCAN`，名字就是干净的。
>
> 对端已有第 19 条要求（参数个数 + 名称空白校验，工具侧自动替换），修好后这条不再需要手动规避。

### 反面：手工敲命令（仅在没开工具时）

```
KEY ADD 手机-03 - 62726964676500000000000000000003
```

三条硬规矩，违反会**静默失败**（不报错，但永远匹配不上）：

| 规矩 | 原因 |
|---|---|
| 名字里**不能有空格** | 命令按空格切分，带空格会让后面字段整体错位 |
| 跳过地址只能用 `-` 占位，且**不能写成两个空格** | 两个空格会被合并 → UUID 被当成地址 |
| UUID 用手机页面「复制 32 位」，**不要手打** | 少数一位就是另一把钥匙 |

> **已知缺陷（对端未修）**：`-` 会被原样存成地址 `"-"`，于是**第二台手机再传 `-` 会覆盖第一台**。
> 所以每次改钥匙前先 `KEY LIST` 抄下现有条目，改完再 `KEY LIST` 对数。
> 该问题已写进要求单第 7 条，等对端修。

## 五、档位与省电（这是本功能的核心行为）

手机侧不是「一直全速播」，而是按「有没有人在用车」自动换档：

| 档位 | 什么时候 | 间隔 | 对端判近速度 |
|---|---|---|---|
| **亮屏提速** | 屏幕亮起后的 **2 分钟**内（灭屏不打断，走完这 2 分钟） | **100ms** | 约 **1.5 秒** |
| **快速** | App 在前台 **或** 极空已连接 | 250ms | 约 2~3 秒 |
| **宽限** | 刚从上面两种状态掉下来 | 250ms，持续 **5 分钟** | 同快速 |
| **慢速保底** | 宽限结束，且不在静默时段 | **1000ms** | 约 6~10 秒 |
| **静默（停播）** | 宽限结束 + 落在静默时段 | 不播 | 不通电（对端 ~75 秒后断电） |

### 为什么要「亮屏提速」

后台 1000ms 时，对端要撞上 25% 的扫描窗口才能收到一帧，还需连续 3 帧才判近——
实测「走到车边 → 通电」约 **8 秒**，等得让人怀疑坏了。

所以在**屏幕亮起时**临时切到 100ms，2 分钟后自动回落。因为人要用车时几乎都会掏手机亮屏，
这是最便宜也最准的「我来了」信号：

- 亮屏瞬间到 2 分钟内 → 走近 **约 1.5 秒**通电
- 2 分钟后（宽限内）→ 250ms，约 3 秒
- 更久之后 → 1000ms，8 秒

耗电可以忽略：100 次/天 × 2 分钟 ≈ **3 mAh ≈ 0.07%/天**（4500mAh 电池），
相当于多亮屏 1 分钟。

> 注意：手机在兜里**黑屏**、直接走到车边，仍然是 1000ms → 8 秒。
> 这是有意保留的省电取舍——不想让它变慢就走「亮屏」这条最短路径。

### 静默时段（默认 21:00–05:00，可改可关）

夜里手机放床头，一直全速播是纯浪费。所以静默期内：

- **App 在前台** → 照常快速广播 ✅
- **极空已连接** → 照常快速广播 ✅
- **两者都没有** → **停播沉睡**

**夜间要用车怎么办**：打开 App（立刻恢复 250ms），或者让极空连上。
这是**有意的产品行为**，不是故障。静默生效前 5 分钟会发一条提醒（每天一次，可关）。

### 为什么中间要「宽限 5 分钟」

下车搬东西、锁车、孩子在旁边转一圈——如果一离开前台就掉到 1000ms，这段时间车会判远。
5 分钟宽限让「下车但还在车旁」保持全速。

### 省电预期

| 状态 | 量级 |
|---|---|
| 快速广播 | 0.3~0.8 mA，折算 0.5~2% / 天 |
| 慢速保底 | 更低（约 1/4 占空比） |
| 静默 | 0（只有前台服务本身） |

真机实测方法见设计文档 §13。判据：**≤2% / 天可接受**。

## 六、界面说明

设置分区卡片（一眼要看的）：总开关 / 编号 / 当前档位与原因 / 详情入口。

详情页包含 12 块：

| 块 | 用途 |
|---|---|
| 当前状态 | 档位、生效原因、已播时长、**保活方式说明** |
| 开关与编号 | 启停、改编号 |
| 标识 | 32 位 / 带连字符 UUID + 一键复制 |
| 设备名 | 当前系统蓝牙名；「按编号改名」（会改手机整体蓝牙名，二次确认） |
| 自检 | 边播边扫 5 秒（**只有点击时执行**）；四档结论，见第七节 |
| 发射功率 | 低 / 中 / 高，默认**中**；裤兜遮挡重就选高 |
| 时段静默 | 起止时刻 + 静默前提醒开关 |
| 系统限制 | 电池优化白名单状态与入口 |
| 高级：UUID 前缀 | 30 字符 hex（改 = 换整套钥匙，所有对端重新登记） |
| 安全边界 | UUID 可被复制、无防伪的说明 |

### 「保活：每 60 秒强制重建一次」是什么意思

系统/ROM 会在省电、射频抖动、蓝牙开关时**静默停掉广播且不回调**。而 Android **没有任何 API
能查询「广播现在是不是真的在发」**——所以我们不去"查"，而是每 **60 秒主动重建一次**
（停 → 立即重开，空窗约 30~100 毫秒）。

- 对端 15 秒才判"远"，这点空窗它完全感觉不到
- 60 秒的意义：对端「15 秒判远 + 60 秒断电 ≈ 75 秒断电门」，只有 ≤60 秒的周期能救回来，
  否则一次静默停播就会导致**行车中断电**
- 代价：约 0.1 mAh/天（0.002%），测不出来

> 所以详情页那行是**说明**，不是计数值——不存在「涨到几百次说明有问题」这种判断。
> 真要知道广播在不在发，唯一权威是 **ESP32 侧 `SCAN`**。

## 七、FAQ / 排障

### 到车边不通电

按顺序查（**90% 是前三条**）：

1. **是不是静默时段**（21:00–05:00）且 App 在后台、极空没连 → 打开 App 即恢复
2. **看通知在不在**：通知没了说明服务被杀 → 打开 App 会自动拉起
3. **在详情页点「开始自检」**：只有显示「已确认在播（-xx dBm）」才是手机侧无问题的**强证据**；
   显示「无结论 · 扫描正常」**不代表有问题**（见下一节），此时直接跳到第 4 步
4. **对端 `KEY LIST` 核对**：UUID 与手机页面逐字符一致？
5. **对着 `KEY LIST` 看名称**：如果你手机叫 `OPPO Reno9`，而列表里出现的是 `OPPO`、
   地址是 `Reno9` —— 说明登记时名字空格把字段冲散了，删掉重登（名字改成 `OPPO-Reno9`）
6. **对端 `SCAN` 看信号值**：贴车时应约 -60~-75；如果贴车都只有 -90，
   是手机塞太深/人体遮挡 → 换发射功率「高」，或把对端 `rssi_on` 放宽

### 自检显示「无结论 · 扫描正常」

**这是正常现象，不是故障。** 多数手机的 BLE 芯片单天线分时收发，**不会把自己发出的包报给扫描器**，
所以手机上永远扫不到自己。它与"钥匙好不好使"无关——实测 ESP32 能扫到、车正在通电时，
手机自检同样扫不到自己。

四档结论的含义：

| 显示 | 含义 | 要做什么 |
|---|---|---|
| 已确认在播（-xx dBm，N 帧） | 强证据，确实在发 | 无需处理 |
| 无结论 · 扫描正常 | 扫到了**别的** iBeacon，只是没自己 → 机型限制 | **不用管**，去 ESP32 侧确认 |
| 无结论 · 附近无信标 | 只扫到别的蓝牙设备，附近没有可比对目标 | 不用管 |
| 无结论 · 未收到任何包 | 5 秒一个包都没收到；可能附近确实没有 BLE 设备 | 若你确定旁边有耳机/手环也扫不到，才查是否开着极空扫描页 |
| 无法自检 | 蓝牙关 / 缺「附近的设备」权限 / 启动失败 | 按提示开蓝牙或授权 |

> 唯一权威永远是 **ESP32 侧 `SCAN`**：手机侧没有任何手段能证明"包真的在空中"。
> 因此自检**只会给出"已确认在播"这一种肯定结论**，其余都是"无法判断"——这是刻意的，避免误报。

### 车反复通电断电（继电器咔咔响）

两把钥匙一近一远时，对端旧逻辑会「一把走远就整体断电」。这是对端已知问题，
要求单第 18 条已要求改成「任一近即通电、全部远离才断电」。在它修好前，
**先只登记一把手机钥匙**，不要同时挂手环。

### 通知栏一直有「钥匙 NN 广播中」，能关吗

不能，这是 Android 对后台广播的硬要求（前台服务必须有常驻通知）。
关掉总开关即消失。通知上有「停止」按钮，点了会**同时关闭总开关**。

### 换了手机 / 重装 App

编号会丢（存在 App 私有目录）。重新填**同一个编号**即可，对端不用重新登记。
换编号则必须重新登记。

### 两台手机能共用一把钥匙吗

能，但**不推荐**：填同一个编号即同一个 UUID。缺点是删一把等于两把都失效。
正确做法是各用各的编号，对端登记两条。

## 八、配置项一览

| 项 | 默认 | 存在哪 | 说明 |
|---|---|---|---|
| 总开关 | 关 | App 本地 | 关掉立即停播并撤通知 |
| 编号 | **空** | App 本地 | 00~99，空则不允许开启 |
| UUID 前缀 | `627269646765…0000`（30 位） | App 本地 | 改 = 换整套钥匙 |
| 发射功率 | 中（-7dBm） | App 本地 | 部分 ROM 会忽略此项 |
| 静默时段 | 开，`21:00`–`05:00` | App 本地 | 支持跨午夜，只关后台慢速档 |
| 静默前提醒 | 开 | App 本地 | 每天最多一次 |
| 设备名 | 系统蓝牙名（不改） | 系统 | 想带编号需「按编号改名」 |

对端侧（不在本 App 内，改需连 ESP32）：

| 项 | 现值 | 位置 |
|---|---|---|
| `rssi_on` / `rssi_off` | -80 / -90（全局一对） | `config.json` |
| `loss_timeout_s` | 15 秒 | `config.py` |
| `power_off_delay_s` | 60 秒 | `config.py` |
| 钥匙上限 | 10 把 | 固件硬限制 |

> `rssi_on/off` 目前是**全局唯一一对**（手环和手机共用），手机可能需要单独标定。
> 每钥匙独立阈值已写进要求单第 17 条。

## 九、排障命令（开发/自测用）

```bash
# 1. 广播会话在不在（看有没有 advertising set）
adb shell dumpsys bluetooth_manager | grep -i advertis -A 3

# 2. 服务在不在
adb shell dumpsys activity services my.bridge.com | grep -i blekey

# 3. 通知在不在
adb shell dumpsys notification --noredact | grep -i "blekey\|钥匙"

# 4. 日志（档位切换、例行重建、失败原因）
adb logcat -s BleKey BleKeyService BleKeySelfCheck BleKeyName
```

日志里的关键行：

| 日志 | 含义 |
|---|---|
| `档位 FAST → SLOW（后台慢速保底…）` | 宽限到期，正常降档 |
| `强制重建广播会话（mode=SLOW）` | 每 60 秒的例行重建（debug 级，正常） |
| `广播启动失败 code=3 广播数据超长` | 组包超 31 字节（正常不会出现，出现即是回归） |
| `已发静默前提醒：5 分钟后进入 21:00` | 静默提醒已发 |

## 十、已知限制（写在这里，避免当成 bug）

| # | 限制 | 影响 | 后续 |
|---|---|---|---|
| 1 | **没有回执**：手机永远不知道对端认没认出来 | 只能靠自检/对端串口确认 | 对端需加回执通道，当前无 |
| 2 | **UUID 无防伪** | 不防盗 | 需换 BLE 连接 + 挑战应答 |
| 3 | 静默期内后台停播 | 夜里到车边不通电 | 有意设计；打开 App 即恢复 |
| 4 | 广播名只能用系统蓝牙名 | 想带编号得改全局蓝牙名 | Android 无此 API |
| 5 | 对端阈值全局一对 | 手环/手机可能需不同值 | 要求单第 17 条 |
| 6 | 对端「一把走远就断电」 | 多设备互相干扰 | 要求单第 18 条 |
| 7 | 对端扫描列表的 **MAC 列对手机无意义**（手机地址随机） | 登记必须看 UUID 列，别看 MAC | 不是 bug；一轮扫描内同一台设备只有一行 |
| 8 | `-` 占位会互相覆盖 | 第二台手机顶掉第一台 | 要求单第 7 条；当前先 `KEY LIST` 留底 |
| 9 | **名字含空格会登记成死记录** | 出厂名带空格（`OPPO Reno9`）时，用工具添加会字段错位，看起来成功但永远不通电 | 要求单第 19 条；当前靠「按编号改名」或手工把空格写成 `-` 规避 |
| 10 | **黑屏放兜里走近要 8 秒** | 只有亮屏后 2 分钟内才是 1.5 秒；黑屏状态仍是 1000ms 慢速档 | **有意取舍**（省电）。嫌慢就按一下电源键 |
| 11 | **自检扫不到自己** | 多数机型不上报自发广播，所以自检常显示「无结论」 | **不是 bug**，判断口径见第七节；权威永远是对端 `SCAN` |

## 十一、验收

完整验收流程见 [`docs/research/ble-key-acceptance.html`](../research/ble-key-acceptance.html)（可勾选清单）。
本文档只给「最小可用判据」：

1. 开启后通知显示「钥匙 NN · 广播中」
2. 对端 `SCAN` 能看到 UUID 完全一致的那一行
3. 贴车通电、拿走约 75 秒断电
4. 切到后台等 5 分钟 → 通知变「慢速保底」
5. 杀进程后 1 分钟内通知自动回来
6. 蓝牙关了再开 → 自动恢复

## 十二、不想逐项测？挂着跑 + 上传日志（v0.3.008 起推荐）

50 项验收逐条手点不现实，而且「后台挂 8 小时还灵不灵」本来也只能靠时间验证。正确用法：

### 12.1 三步

1. **开着不用管** —— 总开关打开、编号已设，正常用车。跑 1~3 天。
2. **看一眼详情页「运行概况」卡片** —— 设置 → 连接 → 蓝牙钥匙：
   - 服务启动、巡检轮数、最后巡检、累计广播、广播失败、上次断档
   - 数字正常（失败 0、巡检 ≈ 挂机分钟数）就不用管了
3. **上传日志** —— 设置 → 连接 →「上传诊断日志」。建议**每天点一次**（10 秒的事）：
   - 单次上传最多带 **5000 行**，而全机各模块每天产生约 **4000~7000 行** → 一次上传只覆盖最近 **约 1 天**；
   - 服务端按设备保留最近 **20000 行** → 约 **3~4 天**窗口，所以偶尔忘一两天也还有缓冲；
   - 重复上传自动去重（`device_id + ts + line_hash`），多点几次没有副作用。

### 12.2 上传后日志里能查到什么

上传流最后会多出一行（按 tag `BleKeySummary` 过滤即可第一眼看到）：

```
[BleKeySummary] v0.3.008 钥匙=03 启用=是 功率=中（约 -7dBm，默认） 静默=21:00–05:00
| 服务创建=7次 巡检=4321次 最后巡检=11-18 15:30:00 失败=0次 累计广播=68小时12分
档位轮数=SLOW2980/FAST1100/QUIET241 上次断档=2分13秒 上次销毁=被动销毁 | 首次启用=11-15 09:12:03
```

另有四类事件日志（tag 可直接过滤）：

| tag | 内容 |
|---|---|
| `BleKeyHealth` | 服务创建/销毁、断档告警（> 2.5 分钟判「疑似被杀」）、失败原因变化 |
| `BleKeyService` | 档位切换、亮屏提速、蓝牙状态变化、静默提醒、每 10 轮一条巡检汇总 |
| `BleKey` | 广播启动/停止/失败码、例行重建（D 级） |
| `BleKeySummary` | 上面那行摘要 |

### 12.3 判读口诀

| 指标 | 正常 | 异常信号 |
|---|---|---|
| 失败 | 0 次 | > 0 且在涨 → 查 `BleKeyHealth` 的 W 级原因（权限被撤 / 广播槽被占） |
| 巡检轮数 ÷ 挂机分钟数 | ≈ 1 | 明显偏小 → 服务被反复杀 / 手机重启过 |
| 累计广播时长 | 接近挂机时长（除静默时段） | 远小于 → 长期未广播或静默配错 |
| 服务启动次数 | 个位数 | 几十次 → ROM 强回收，配电池白名单 |
| 上次断档 | < 2 分钟 | 数小时 → 中间死过，看「上次销毁」区分主动/被动 |

### 12.4 为什么不建议一直插 adb

- 灭屏后无线 adb 常掉，插线又妨碍正常使用；
- `adb logcat` 只有实时窗口，看不到「昨天夜里发生了什么」；
- 上传日志带磁盘历史（跨进程、跨重启），才是长期观测的正确通道。

> 紧急排查某个瞬间（比如开关蓝牙的时序）才用 `adb logcat -s BridgeDiag:I`。

### 12.5 日志会自动清理，你不需要手动删任何东西

三层都是自动的，**没有任何「定期清日志」的操作需要做**：

| 层 | 机制 | 上限 | 触发时机 |
|---|---|---|---|
| 手机内存缓冲 | 环形队列，满了挤掉最旧 | 600 条 | 每条日志写入时 |
| 手机磁盘文件 | `bridge.log` 写满 1MB 就滚动成 `.1`，`.1→.2…`，删掉 `.5` | **约 6MB**（主文件 + 5 个滚动文件） | 主文件满 1MB |
| 服务端 MySQL | 每次上传入库后，删掉该设备第 20000 行之后的旧行；另有超龄清理 | **20000 行/设备 + 30 天** | 每次上传时 / 每小时最多一次 |

所以长期挂着跑，磁盘占用会稳定在 6MB 左右并自行循环，数据库也会自剪到 20000 行。
**代价**是「旧日志会被新日志挤掉」——这不是故障，是设计。想留住某段历史，就在那之前点一次上传，
把数据落到服务端（服务端保留 3~4 天）或直接看详情页「运行概况」的累计数字（那个是永久的）。

> 管理后台的「清除全部日志」按钮会下发 `clear_log`，那才是唯一会主动删除的动作，平时不会自己触发。
