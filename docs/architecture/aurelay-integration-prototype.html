一、一句话结论

可行，但不是「搬运 Aurelay」，而是「抽取其音频中继内核，重写到 Bridge 的命令/服务体系中」。

Aurelay 有约 30 个 Kotlin 文件，但真正属于「中继模式」的内核只有 5~6 个文件（约 2000 行）：流协议 + 接收播放 + 中转客户端。其余（UI 巨型单函数、广告、内购、电脑放音、保活、诊断）要么 Bridge 已有等价物、要么应砍掉。

核心难点不在「抄代码」，而在 Bridge 的中转链路要不要复用自家 WS 通道，还是复用 Aurelay 的独立中转服务器 —— 这是决定工作量和架构形态的第一岔路。

二、Aurelay 到底在做什么

2.1 产品形态：两种模式

① 手机放音（接收端） —— 「电脑声音 → 手机播放」

手机当电脑的「无线音箱/耳机」。电脑把声卡输出编码成 Opus，推给手机，手机解码播放。这是 你要的「中继模式」。

② 电脑放音（发送端） —— 「手机麦克风 → 电脑播放」

手机当电脑的「无线麦克风」。采集手机麦克风，Opus 编码后推给电脑。这是「电脑放音」模式，建议砍掉。

2.2 中继模式（手机放音）的完整链路

三、精简建议：保留什么、砍掉什么

3.1 保留（中继内核，约 5 文件 / 2000 行）

必须保留
  • RelayProtocol.kt + RelayClient.kt：出站 WebSocket 中转客户端，含心跳（30s）、退避重连（1/2/4/8/16/30s）、DNS 兜底、优雅关闭、管道重建。这是「中继」的命脉。
  • OpusDecoder.kt：系统 Opus 解码。注意「统一 CSD」83 字节这个坑（AOSP C2SoftOpusDec 要求 AOPUSHDR+AOPUSDLY+AOPUSPRL 三段齐了才解码），是血泪教训，必须原样保留。
  • AURL 流协议 + AudioTrack 播放：从 AudioRelayService 里抽出，剥离诊断/链路切换，重写为 Bridge 风格。

3.2 砍掉（与「中继模式」无关）

整体删除
  • 电脑放音整套：OpusEncoder + AudioCaptureService + DeviceStore（我的电脑列表）—— 这是「手机→电脑」方向，不是你要的中继。
  • 广告 / 内购：AdsManager、BillingManager、PurchaseManager、SmartAdBanner、IapAdsActivity，及 buildConfigField ENABLE_ADS、billing/ads 依赖。
  • 局域网直连（内网模式）：ServerSocket :5000、TLS 整套、auto/lan 链路决策 —— 你已明确「不考虑内网模式」，链路固定走 relay，NetworkWatcher 的 auto 决策也随之砍掉。

3.3 复用 Bridge 已有的（不要重复造轮子）

Bridge 已有等价物，Aurelay 的对应部分直接丢弃
  • 保活体系：Bridge 的 core-keepalive 已有 SilentPlayer / ResourceHolder / KeepAliveService / OnePixelOverlay / BootReceiver，且比 Aurelay 的更贴合本项目（无声播放开关等）。Aurelay 的整套保活直接不用。
  • 设置存储：Bridge 用 DataStore（core-storage），Aurelay 用 SharedPreferences。中继的服务器地址/端口/开关走 Bridge 的存储。
  • 日志：Bridge 用 Timber，Aurelay 用自研 DiagLog。直接砍 DiagLog，用 Timber。
  • 网络：Bridge 已有 OkHttp 依赖吗？—— 见决策点 D2。

3.4 精简后：Aurelay 30 文件 → 集成进 Bridge 约 4~5 个新文件

四、集成到 Bridge 的两种路线

这是最关键的架构分岔。核心问题是：电脑推来的音频，走哪条通道到 Bridge 设备？

路线 A：复用 Aurelay 的中转服务器

Bridge 内置 RelayClient，直接连 Aurelay 已有的 039039.xyz:15151 中转服务器，电脑端继续用 Aurelay 的 send_audio.py / PC 客户端。

优点：电脑端零改动、立即可用；中转服务器已就绪。

缺点：依赖第三方/外部服务器；Bridge 的鉴权、设备体系与 Aurelay 服务器脱节。

适合快速验证

路线 B：走 Bridge 自有 WS 通道

把「中转」能力整合进 Bridge 自己的服务端（FastAPI + WS）和命令体系：管理后台发「音频中继」命令，服务端把音频流转发给指定设备。

优点：与 Bridge 现有「设备管理 / 命令下发 / 媒体流」体系统一；无需外部服务器。

缺点：服务端要新增「音频房间配对 + 转发」逻辑（可参考 Aurelay 的 center-server）；工作量大。

长期正解
建议：先 A 后 B 路线 A 用最少改动把「中继内核」跑通、验证 Opus 解码/播放链路无误；确认稳定后再把中转服务器替换为 Bridge 自有的（路线 B）。两条路线的 客户端内核（RelayProtocol + RelayClient + OpusDecoder + AudioTrack）完全一致，只是 RelayClient 连的 URL 不同 —— 因此内核先做，路线可平滑切换。

五、推荐架构（原型模型）

把「音频中继」作为 Bridge 的一个 新命令（类比已有的 music / screen_live），纳入现有命令目录体系。

5.1 中继命令的交互流程

  1. 1管理后台下发 audio_relay 命令（参数：中转服务器 host:port、是否自动开始）
  2. 2服务端经 WS 通道下发到指定设备（复用 Bridge 现有命令链路）
  3. 3设备 CommandExecutor 启动 AudioRelayService：出站连中转服务器，注册为接收端 R
  4. 4电脑端（推流端 S）连同一中转服务器，建立房间配对
  5. 5音频字节经中转服务器透传，设备端 OpusDecoder 解码 → AudioTrack 播放
  6. 6设备经 WS 回执「已连接/播放中/音量」，管理后台实时展示

六、关键决策点与风险

编号决策点建议
D1路线 A（复用 Aurelay 中转服务器）还是 B（Bridge 自建中转）？先 A 验证内核，后切 B 长期统一
D2Bridge 是否已有 OkHttp 依赖？（RelayClient 强依赖 OkHttp WebSocket）core-network 需确认；没有则补，或用 Bridge 已有 WS 客户端改造
D3「电脑放音」要不要？默认砍；若未来要「手机麦克风→电脑」再补 OpusEncoder
D4中继服务器鉴权（token/deviceId）路线 B 下复用 Bridge 设备标识；路线 A 沿用 Aurelay 的 token
D5Opus 解码的「统一 CSD」坑必须原样保留，否则永久静音（这是 Aurelay v1.4.5 血泪修复）

风险清单

需重点关注
  • AudioTrack 状态陷阱：stop() 不改变 state，复用「已停止」音轨会「连着没声」；会话结束只 pause+flush、不 release。这些坑已在 Aurelay CHANGELOG 里反复踩过，移植时必须保留注释。
  • 中转残留帧震荡：断线重连时的「旧会话残留帧 → 误判 → 重连死循环」，Aurelay 用「扫描魔数 + 受控重连 + 会话代次」解决。这些是稳定性关键，不能精简掉。
  • 音轨并发：切链路时多路流并发写音轨会错乱，靠「会话代次」守卫。若只保留 relay（不切链路），风险大降，可简化。
  • 保活与中继的无声播放让位：真实音频播放时 SilentPlayer 要让位（避免底噪）。Bridge 的 SilentPlayer 已有 setScenarioAllowed，需对接。

七、落地步骤建议

步内容产物
1确认 D2（OkHttp 依赖）、D1（路线），补齐 Bridge 侧依赖依赖就绪
2移植 RelayProtocol + RelayClient（去 DiagLog→Timber，去电脑放音 sendAudio）内核可出站
