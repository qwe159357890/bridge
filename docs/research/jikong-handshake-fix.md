# 极空「半死链唤醒」握手修复专档

> **文档定位**：专门追踪**单一问题**——「靠近能立马发现并建链，但要 3~4 轮 12s 超时直连重建才收到数据（0x02）并播报」的排查与修复。
> 本档回答三个问题：**① 进度到哪了 ② 每个实验改了哪个变量、结果如何 ③ 怎么一键回到「功能跑通」状态、以及三个实验全失败后还能做什么**。
>
> 与主调研文档的关系：`docs/research/jikong-proximity-autoconnect.md` §四 是**剖析**（为什么多轮），本档是**执行台账**（怎么测、测到哪、怎么撤）。两者配合，本档不再重复剖析细节，只记录可执行的状态与结论。

---

## 一、问题定义（冻结，不再改动）

| 项 | 内容 |
|---|---|
| **现象** | autoConnect 靠近后**立即发现并建链**，但 BMS 只回 `AT\r\n` 与偶发 0x01，进不了 0x02 数据流；要经 **3~4 轮 12s 超时直连重建**（近 1 分钟）才收到数据、播报电量 |
| **可听见标志** | 保护板每次被唤醒会「滴滴滴」；官方 APP 只响 1 次，我们响 3~4 次 |
| **对比基准** | 官方 APP 同场景**一次交互即成功**；我们手动直连（BMS 已醒）第 1 条链路也出数据 |
| **根因定性** | BMS 蓝牙模块（CC2541/BT05 透传桥）在 MCU 休眠时「广播在、连接能建、但命令不转发」＝**半死链**；唤醒它需要正确的「连接事件频率 + 触发策略」，而我们当前策略会在 MCU 即将苏醒时打断唤醒 |
| **已排除** | JK02 协议本身正确（开源社区 BHP1000/syssi/peff74 实证 + 手动直连第 1 链路出数据）；官方无独立「神秘激活帧」 |

**一句话**：不是协议问题，是「半死链唤醒」的**触发策略**问题。要复刻官方「高频连接事件 + 只发一次命令耐心等」，逐变量单测定位。

## 三、实验纪律（单变量铁律，避免「找不到原因」的根源）

1. **一次只改一个变量**：每个实验只动一个差异点，其余保持与上一个实验完全一致。改多个变量 = 结果无法归因 = 白测。
2. **改前必留档**：在 `docs/dev/jikong-change-ledger.md` 登记改前原文（含 git 未跟踪文件逐字抄录）→ 改 → 回填改后 + 回滚配方。见模板 §8。
3. **每个实验独立提交 + 独立 tag**：提交信息带实验编号（如 `exp1: ...`），tag 用版本号（`v0.2.110`）。回退即 revert 该提交。
4. **验证条件统一**：所有实验共用同一套真机验证步骤（见 §五），结果才能横向对比。
5. **结果回填本档**：每做完一个实验，无论成败，立即把「结果 + 结论 + 是否命中」写回 §四矩阵和 §五卡片。不写 = 进度丢失。

## 五、统一真机验证步骤（每个实验共用）

1. **制造半死链**：保护板闲置 ≥10 分钟（让 MCU 进入休眠）。
2. **打开开关**：确保「靠近自动连接」已开启、默认设备已设置、播报已开。
3. **熄屏放兜里**：手机靠近保护板（模拟真实「人走近」场景，非手动进页）。
4. **计时 + 数蜂鸣**：从靠近开始计时，记录：
   - **第几轮 12s 才收到 0x02 播报**（第 1 轮 = 一次成功）
   - **保护板「滴滴滴」响了几次**（期望 1 次）
   - 总耗时（期望 ≤30s，理想 5~15s）
5. **查日志佐证**：从服务端拉设备日志（`device_logs` 表），数「12s 超时重建 / startProximityReconnect」出现的次数，与蜂鸣次数、播报时机对照。
6. **重复 3 次**取稳定结论（半死链有随机性，单次不可信）。

**成功标准**：闲置 ≥10min 后靠近，**第 1 条链路内**收到 0x02 并播报、蜂鸣 ≤1 次、无 12s 断开重建。

## 六、实验卡片（逐个回填）

### 实验①：requestConnectionPriority(HIGH)　—　0.2.110

- **唯一改动**：`JikongBleClient` 在 `onConnectionStateChange(STATE_CONNECTED)` 回调里、发 `requestMtu(256)` 之前，加 `runCatching { g.requestConnectionPriority(BluetoothGatt.CONNECTION_PRIORITY_HIGH) }`。
- **保持不动**：0x96 ramp、12s 重建、挂起逻辑全部不变。
- **假设**：官方靠 7.5ms 连接事件持续唤醒 MCU，我们默认 30~50ms 事件频率不够。
- **改码状态**：✅ 已改（提交 `9ea241a`，版本 0.2.110，编译 BUILD SUCCESSFUL）。
- **结果**：✅ 已真机验证（用户 2026-11-08 15:00 反馈 + 日志实证，设备 f2c38ebee251a196）。日志 14:52:38 靠近 → 14:52:52 收到 0x02 播报 = **14 秒**，「主动重建链路」只到**第 1/3 次**即成功（基线 v0.2.109 是 3~4 轮 ≈ 1 分钟）。MTU 协商到 **303**（此前 256）。
- **结论**：**半命中**——`requestConnectionPriority(HIGH)` 显著提高「直连重建」成功率（3~4 轮→1 轮），但**首建链（autoConnect）仍是半死链**：14:52:38 建链后 0x96 连发 11 次（14:52:40~50）无 0x02，14:52:51 触 12s 超时断开、14:52:52 直连重建**立即**出数据。
- **★ 关键线索**：日志显示 BMS 苏醒延迟约 **13~14 秒**（重建时恰逢苏醒）。我们的 12s 超时**刚好卡在 BMS 苏醒前一点点断开重建**。→ 强烈指向实验②：放宽/移除 12s 重建、回到「耐心等」，有望让**首建链直接在原链路上等到数据**（= 官方一次成功，无需断开重建）。

### 实验②a：只放宽 12s 重建阈值 → 20s　—　0.2.111

- **唯一改动**：`JikongController.startPolling` 启动 ramp 的 `now - connectAt > 12_000` → `20_000`（12s→20s）。
- **保持不动**：0x96 补发频率（1.2s）、3 次重建保底（`datalessRecycles < 3`）、`requestConnectionPriority(HIGH)`（实验①已合入）、挂起逻辑。
- **假设**：BMS 苏醒延迟 ~14s，12s 断开恰好卡在苏醒前；放宽到 20s 让首建链直接在原链路等到 BMS 醒来自动出数据（= 官方一次成功）。
- **保底**：若 20s 不醒仍走 3 次重建（共 60s）后进入「保持链路继续 ramp 耐心等」，不会「一直卡死」。
- **改码状态**：✅ 已改（提交 `82cdd83`，版本 0.2.111，编译 BUILD SUCCESSFUL）。
- **结果**：❌ 已真机验证（用户 2026-11-08 17:29 反馈「靠近几分钟不播报」+ 日志实证，设备 f2c38ebee251a196，v0.2.113 含 20s 阈值）。日志时间线：17:21:02 autoConnect 首建链→半死链持续 23s（0x96 连发只回 AT，BMS 未在 20s 内苏醒）→17:21:25 20s 阈值触发直连重建→**只活 3s 就 status=8**（17:21:28，直连唤醒失败）→退回 autoConnect 重挂→第 3 次又半死链→第 4 次又 status=8→第 5 次（17:22:37）才收到 0x02 出数据（17:22:39）并播报（17:22:41）。**总计 5 次连接、约 97 秒**。
- **结论**：**未命中且更差**（实验① 12s 阈值 + HIGH 是 14s 出数据）。关键新线索：①BMS 苏醒延迟**有随机性**——实验①时 ~14s、这次 >23s 仍未醒；②「断开立即直连」在 BMS 深睡时反而 3s 就 status=8 快速超时。⇒ **「等待固定时长 + 重建」本质是赌苏醒时机，不可靠**，方向应转向 §七 ★★☆ `requestConnectionParameter` 强制连接参数（BMS 可能忽略了 `requestConnectionPriority` 的「请求」）或 ★★★ HCI Snoop 字节级对比官方 APP。

### 实验④：反射 requestLeConnectionUpdate 强制 7.5ms　—　0.2.114

- **唯一改动**：`JikongBleClient` 连接后反射调用 AOSP 隐藏 API `requestLeConnectionUpdate(6, 6, 0, 200, 0, 0)`（min=max=7.5ms、latency=0、timeout=2s），配合 `requestConnectionPriority(HIGH)` 一并下发。
- **同步回退**：`JikongController` 20s 阈值 → **12s**（撤销实验②a 的失败改动——②a 已证伪 20s 更差，回退 12s 不是新变量，是恢复实验①的基线）。
- **前提**：实验②a 未命中（已证伪）后转向。公开 API `requestConnectionPriority` 在 Android 6+ 仅映射 11.25~15ms（AOSP GattService 实证），无法真 7.5ms；官方「一次唤醒」疑似靠真 7.5ms 的高频连接事件，故反射 @hide 方法强制。
- **改码状态**：✅ 已改（`JikongBleClient.kt` 加 `forceLeConnectionParams`；`JikongController.kt` 20s→12s；版本 0.2.114，编译 BUILD SUCCESSFUL）。
- **★ 归因纪律**：反射可能失败（方法不存在/签名变/被拒），**日志必须区分**——
  - `实验④强制连接参数：requestLeConnectionUpdate 反射成功` → 请求已下发，看首建链是否一次出数据；
  - `实验④反射 requestLeConnectionUpdate 失败（降级 HIGH）` → 本实验未生效，等效只有 12s 回退，结论应记为「反射失败，7.5ms 未验证」。
- **结果**：❌ 反射失败（真机日志 2026-11-08 19:31/19:32 实证）——每次连接都打印 `实验④反射 requestLeConnectionUpdate 失败（降级 HIGH）：android.bluetooth.BluetoothGatt.requestLeConnectionUpdate [int, int, int, int, int, int]`。根因：Android 9+ 的 **hidden API 限制**把 `@hide` 方法从反射可见性里移除，`getMethod` 直接抛 `NoSuchMethodException`（方法在 AOSP 源码里是 `public` + `@hide`，但运行时被 blacklist 拦截）。普通反射无法绕过（需 meta-reflection / Unsafe / VMRuntime.setHiddenApiExemptions 等 hack 手段，Android 13+ 进一步收紧，收益低）。
- **结论**：**7.5ms 未验证、未生效**，本实验等效「只有 12s 回退」。但**意外收获**：12s 回退 + HIGH（11.25~15ms）已把靠近自动连接稳定到 **~14s / 1 次重建 / 蜂鸣 1 次**（对比实验②a 20s 的 97s/5 次），这是**可接受体验**。**建议：不再追 7.5ms（hidden API 阻断，性价比极低），把 12s 阈值固化为最终方案**。若日后还想追「一次成功」，唯一靠谱路径是 §七 ★★★ HCI Snoop 字节级对比官方 APP。

## 七、兜底方向（若实验①②③④全部未命中）

> 这是用户最担心的情况。结论先行：**即使三实验全失败，仍有硬手段定位，不会「找不到了」**。按性价比排序：

| 优先级 | 方向 | 做法 | 预期 |
|---|---|---|---|
| ★★★ | **HCI/BT Snoop 字节级对比**（终极手段） | 开发者选项开启「启用蓝牙 HCI 信息收集日志」，分别抓**官方 APP** 与**我们 APP** 各一次连接的完整时序，用 Wireshark 对比：连接参数更新请求、命令字节、时序间隔 | 一锤定音——官方到底多发了什么/时序差在哪，字节级可见 |
| ★★☆ | **`requestConnectionParameter` 更底层** | 不满足于 `requestConnectionPriority(HIGH)`（只是「请求」），直接 `requestConnectionParameter(7.5ms, 0, 0, 0)` 强制连接参数 | 若 BMS 忽略 priority 请求，这才是真正生效的 |
| ★★☆ | **快档重连间隔放宽** | 台账 v0.2.84 遗留嫌疑：重连间隔 800ms→2s，给 BMS 清链时间（当前 proximity 失败即重挂≈高频重连，可能撞 BMS 状态机） | 若「刚断开立刻重连」是诱因，此改动命中 |
| ★☆☆ | **广播间隔实测校准** | nRF Connect 盯 BMS 广播间隔，校准 autoConnect 命中延迟，排除「发现快但连接慢」的干扰项 | 排除变量，非直接修复 |
| ★☆☆ | **半死链 vs 真死链区分** | 分析 `AT\r\n` 响应的具体内容与 0x01 出现规律，判断 BMS 处于休眠的哪个阶段 | 精确定位唤醒窗口 |
| ★☆☆ | **BMS 固件版本确认** | 读设备信息（0x97 响应），确认手头保护板固件版本，社区检索该版本休眠行为 | 排除固件差异 |

**最优先推荐**：一旦实验③也失败，直接上 **HCI Snoop 字节级对比**。它是「官方 vs 我们」的终极裁判，能彻底消除「还有没复刻的神秘步骤」的猜测。抓取方法见 §七附录（待补全，可在执行时按 `adb bugreport` 或开发者选项导出）。
