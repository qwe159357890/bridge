## 一、极空 BMS 是什么

极空（成都极空科技有限公司，官网 `jk-bms.com`）的**锂电池主动均衡保护板（BMS）**，用于锂电池组的充放电保护、主动均衡、温度保护、SOC 估算等。典型应用：储能、两轮/三轮车电池组、户外电源、房车电池等。

关键产品线（资料内规格书）：
- `JK-BD4A8S` / `JK-BD4A24S` / `JK-BD4AxxS`（4A 主动均衡系列，8S~24S）
- `JK-B2A32S-RP`、`JK-BD6AxxS`（2A/6A 主动均衡，多串）
- `JK-PB1A16S` / `JK-PB2A16S`（储能系列，大电流 10P~20P）

**核心能力**：实时电压/电流/温度监测、单体均衡、各类保护（过压/欠压/过流/过温/低温）、SOC/循环次数统计、MOS 管开关控制、低温加热（部分型号）、智能充电器联动（部分型号）。

## 二、通信方式与协议（重点）

极空 BMS 提供**多种对外接口**，资料内有三套协议文档，对应不同物理接口：

| 接口 | 波特率 | 协议 | 文档 |
|---|---|---|---|
| RS485 | 115200 | **Modbus RTU**（寄存器映射表） | `RS485_Modbus通用协议V1.1` |
| RS485/RS232/UART | 9600 | **0xDD 帧**（软件板通用协议） | `软件板通用协议_0xDD帧` |
| RS485/UART/上位机 | 115200 | **NW 帧**（监控平台协议，帧头 `0x4E 0x57`） | `主动均衡保护板RS485接口通用协议V2.0` |
| CAN | 250kbps | CAN 协议 | `CAN协议V2.1` |

**APP 与 BMS 的通信 = 蓝牙 BLE 透传**。BLE 把上述帧协议透传过去（手机当作一个"无线串口"）。

### 2.1 APP 实际用的帧协议（反编译 APK 实证）

从 `JK_BMS_6.4.04.apk` 的 dex 中提取到两类帧特征字节，确认 APP 同时支持：

1. **0xDD 帧**（软件板通用协议，9600 波特率那套）：
   - 帧结构：`起始位(0xDD) + 状态位 + 命令码 + 数据长度 + 数据内容 + 校验(2B) + 停止位(0x77)`
   - 状态位：`0xA5`=读取，`0x5A`=写入
   - 命令码：
     - `0xA5 0x03` 读取基本信息及状态（总电压/总电流/剩余容量/标称容量/循环次数/生产日期/均衡状态/保护状态/剩余电量/MOS状态/串数/NTC个数/NTC温度）
     - `0xA5 0x04` 读取电池单体电压（每串 2 字节 mV）
     - `0xA5 0x05` 读取硬件版本号
     - `0xA5 0x06` 读取用户私有数据
     - `0x5A 0xE1` MOS 控制指令（00=解除、01=关充电、02=关放电、03=同时关）
   - 校验：命令码+长度+数据 累加取反+1

2. **NW 帧**（监控平台协议）：
   - 帧头 `0x4E 0x57`（"NW"），结束标识 `0x68`
   - 数据标识码表（0x79~0xB5）覆盖：单体电压(0x79)、功率管温度(0x80)、电池箱内温度(0x81)、电池温度(0x82)、总电压(0x83)、电流(0x84)、SOC(0x85)、循环次数(0x87)、报警信息(0x8b)、状态信息(0x8c)、以及一堆 RW 参数（保护电压/过流/均衡/温度阈值/串数/容量/MOS开关等）

### 2.2 BLE 服务 UUID（反编译 APK 实证）

从 dex 提取到的 BLE UUID（16-bit 自定义）：

| UUID | 用途 |
|---|---|
| `0000FF10/FF11/FF12-...` | JK BMS 自定义 BLE service + characteristic（主用） |
| `0000FF80/FF81/FF82-...` | 另一组（历史/兼容） |
| `0000ffe0/ffe1/ffe2-...` | 标准蓝牙透传 service（BT05/CC2541 透传模块，`ffe0`=service、`ffe1`=读写特征） |
| `00001101-...` | 经典蓝牙 SPP 串口 |

> **结论**：极空 BMS 的蓝牙本质是「BLE 透传 + 0xDD/NW 帧协议」。不同硬件版本/固件可能用不同 UUID 组（`ff10` 或 `ffe0` 透传）。复刻时需要**兼容多组 UUID 的扫描/连接**，连接后读写特征值即收发协议帧。

## 三、官方 APP 的核心界面（复刻目标）

从字符串与协议反推，官方 APP 主界面大致分这些页（复刻以实际为准）：

1. **设备连接页**：BLE 扫描列表、连接、配对密码、扫码绑定。
2. **实时数据首页**（Dashboard）：总电压、总电流、SOC 大圆盘、充放电状态、剩余容量/循环次数、MOS 状态、均衡状态。
3. **单体电压页**：每串电压柱状/列表、最高/最低/压差高亮。
4. **温度页**：功率管温度、电池温度、NTC 多路温度。
5. **保护/状态页**：各类保护标志位（过压/欠压/过流/过温/低温/短路）、报警信息。
6. **参数设置页**：保护阈值（过压/欠压/过流/过温/低温）、均衡参数、串数/容量/类型、MOS 开关、休眠、加热、专用充电器等（需密码写入）。
7. **控制页**：充放电 MOS 开关、均衡开关、关机/重启、强制加热。
8. **关于/版本**：硬件版本、软件版本、协议库版本、固件升级（OTA）。

## 四、复刻 + 远程中转 总体方案

### 4.1 核心架构

```
        BLE(0xDD/NW帧)          Bridge 主 WS             server(15160)           管理后台
BMS ──────────────────► Bridge手机 ──────────────────► 服务端(server/) ──────────► 极空页面
 (从机)    透传/读写特征     (BLE客户端+协议解析)    (长连接/命令/上报)        (复刻UI+远程交互)
```

- **手机端新增 `jikong` 模块**：BLE 扫描/连接 + 协议帧编解码 + 数据缓存 + 实时上报。
- **手机端新增 `JikongPage`**：加在主页 Tab（组网页之后），复刻官方 APP 的实时页/单体电压/温度/设置/控制。
- **服务端**：新增 `jikong_*` 命令族（读数据、写参数、MOS 控制、重启等）+ 设备上报数据落库。
- **管理后台**：新增「极空保护板」页面（放在「自动化调试台」下方），复刻同一套 UI，展示真实数据并支持远程交互。

### 4.2 三层数据流

1. **命令（后台→手机→BMS）**：后台下发 `jikong_read`/`jikong_set`/`jikong_mos` 等 → 服务器 WS 转发 → 手机 CommandModule 执行器 → BLE 发帧 → BMS 应答 → 回执原路返回。
2. **实时上报（手机→服务器→后台）**：手机连上 BMS 后，周期读取关键数据（或 BMS 主动上报帧），经 Bridge 主 WS `data` 通道推服务器 → 落库/内存 → 后台页面实时刷新。
3. **被动推送（BMS 主动帧）**：BMS 发生保护/报警时主动上报，手机转发服务器 → 后台实时告警。

### 4.3 命令清单（初步，参考命令三步法）

| 命令 | 功能 | 对应帧 |
|---|---|---|
| `jikong_scan` | 扫描附近 BLE 极空设备 | BLE 扫描 |
| `jikong_connect` | 连接指定设备（含配对密码） | BLE 连接 |
| `jikong_status` | 读取实时状态（总压/电流/SOC/温度/MOS/均衡/保护） | `DD A5 03` / NW 读全部 |
| `jikong_cell` | 读取单体电压 | `DD A5 04` |
| `jikong_params` | 读取全部参数 | NW 读全部 / 逐寄存器 |
| `jikong_set` | 写入参数（保护阈值/均衡/串数等，需密码） | `0x5A` / NW 写 |
| `jikong_mos` | MOS 充放电开关控制 | `DD 5A E1` |
| `jikong_balance` | 均衡开关 | NW 写 0x9d |
| `jikong_reboot` | 保护板重启 | NW 0xBB |
| `jikong_shutdown` | 保护板关机 | NW |
| `jikong_pwd` | 修改参数密码 | NW 0x05 对密码 |

### 4.4 实时上报（省电 + 可达平衡）

- 参考既有「主动上报」范式（位置/短信）：**连接态下周期读取**（如 2s~5s 读一次实时数据），数据变化或有报警时立即推；无连接则静止。
- BMS 主动上报帧（保护/报警）优先转发，保证告警实时性。

## 五、需要重点解决的问题 / 风险

1. **BLE UUID 兼容性**：不同固件/硬件用 `ff10` 或 `ffe0` 透传，需**多 UUID 组兼容扫描**，连接时按特征值试探。这是复刻能否"连上真机"的最大不确定点——**强烈建议先拿一块真实极空板 + 一台 Android 手机用 nRF Connect 抓 UUID/特征，确认真机协议后再定编码细节**。
2. **无真机无法闭环**：与 ESP32 继电器集成同款困境——没有极空板实体，BLE 连不上、协议帧发不出。开发只能做到「框架完整 + 协议按文档实现」，真机联调需用户提供板子。
3. **蓝牙权限（Android 12+）**：`BLUETOOTH_SCAN/CONNECT` 运行时权限 + 定位权限（扫描必需），需纳入启动权限申请清单。
4. **BLE 断线重连 / 低功耗**：BLE 连接需处理断线自动重连、手机灭屏后 BLE 是否保活（与主 WS 保活策略区分，BLE 通常不支持灭屏常驻，需评估）。
5. **写参数的安全**：写操作需密码（`0x05` 对密码 + `0xb2` 参数密码），后台远程写必须二次确认，避免误改保护阈值导致电池事故。
6. **协议版本差异**：三套协议（0xDD / NW / Modbus）对应不同固件，APP 用哪套取决于具体板子固件；复刻时**优先实现 0xDD 帧（软件板通用，最简单且 APP 明确在用）**，NW 帧作兼容扩展。

## 七、结论

- **技术可行性高**：极空协议文档齐全（0xDD/NW/Modbus 三套），BLE 本质是透传，APP 复刻 + 手机中转 + 后台远程的方案完全可行，且**官方远程方案依赖额外的 4G-GPS 硬件模组**（APP 内 `4G-GPS远程模组通用协议` 印证），我们用 Bridge 手机当中转站反而**省掉了这个硬件成本**，价值明确。
- **最大风险是"无真机"**：协议虽全但 BLE UUID/特征/实际帧格式需真机确认，建议先做阶段 0 摸底，再投入编码。
- **建议**：先落地「阶段 0 真机摸底 + 阶段 1 客户端 BLE/协议层 + 阶段 2 极空页 UI 框架」，管理后台与命令可在真机协议确认后并行推进。

## 八、实施状态（v0.2.55 已落地，2026-11-05）

按用户「无真机、按文档先实现、复刻全做、三端一起完成」的要求，已完成全量实现：

### 客户端（app/）
- `jikong/JikongProtocol.kt`：0xDD 帧（读 `DD A5`/写 `DD 5A`）+ NW 帧（`4E 57`）编解码，两套协议兼容。

- `ui/JikongPages.kt`：极空页 UI（扫描连接 / 实时 SOC 圆盘 / 单体电压 / 温度 / 保护 / 参数 / 控制 7 区）。
