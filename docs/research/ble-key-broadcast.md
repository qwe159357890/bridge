## 〇、一句话

手机从「扫描者」变成「广播者」：新增 `blekey/` 包，用 `BluetoothLeAdvertiser` 广播一条 iBeacon  
（UUID = 固定 30 字符前缀 + 2 位编号），由车上 ESP32 扫到后按 UUID 匹配、判近、吸合继电器。

**这条链路没有回执**：对端是纯蓝牙版（无 WiFi、无服务端），手机永远不知道对面认没认出自己。  
所以本设计的重量不在组包（约 60 行），而在三件事——**什么时候该播**（§7 状态机）、  
**怎么保证它一直在播**（§8 自愈）、**失效了怎么让人发现**（§11 UI + 通知 + 自检）。

与极空（jikong）的关系：极空是手机当 **central** 连 BMS，本功能是手机当 **peripheral** 被扫，  
API 完全不同、`JikongBleClient` 不可复用；但**保活范式**（`connectedDevice` 前台服务 + `START_STICKY` +  
蓝牙开关守护 + `Application` 幂等拉起）照 `JikongProximityService` 抄。

## 一、术语与边界

| 名词          | 含义                                                    |
| ----------- | ----------------------------------------------------- |
| 钥匙          | 手机广播的那条 iBeacon，身份 = 32 字符 UUID                       |
| 编号          | UUID 末 2 位（`00`~`99`），用户唯一需要关心的东西                     |
| 前缀          | UUID 前 30 字符，默认 `627269646765000000000000000000`，高级可改 |
| FAST / SLOW | 250ms / 1000ms 两种广播节奏（§7）                             |
| 静默时段        | 只关 SLOW 档的时段（默认 `21:00–05:00`），活跃态不受影响                |
| 对端          | 车上的 ESP32（espAutoUnlock），只消费、不改动                      |

## 三、事实基线

### 3.1 对端已固化的硬约定（源码实锤，不可改动）

| 项          | 事实                                                                    | 源码位置                                            |
| ---------- | --------------------------------------------------------------------- | ----------------------------------------------- |
| 识别方式       | 主动扫描 `gap_scan(..., True)`；name / mac / uuid **任一命中即命中（OR）**          | `ble_scanner._scan()`、`key_matcher._find_key()` |
| iBeacon 解析 | `<len> FF 4C 00 02 15 <UUID16> <Major2> <Minor2> <Tx1>`，要求 `len ≥ 21` | `ble_scanner.parse_ibeacon_uuid()`              |
| UUID 比对    | **完整 32 字符、小写、无连字符**，字符串相等                                            | `key_matcher._normalize()` / `_find_key()`      |
| 判近         | `rssi ≥ rssi_on` 且**连续 3 帧**                                          | `hit_frames = 3`                                |
| 判远         | `rssi ≤ rssi_off` 连续 2 帧，或**失联 15 秒**                                 | `far_frames = 2`、`loss_timeout_s = 15`          |
| 断电         | FAR 持续 **60 秒**（下限 30，只许调大）                                           | `power_off_delay_s = 60`、`ignition.py`          |
| 扫描节奏       | 中档 200/50（25%）；**一命中立即升快档 100/60（60%）**，10 秒无帧回落                      | `SCAN_MODES`、`_BOOST_HOLD_MS = 10000`           |
| 钥匙上限       | 10 把                                                                  | `config_mode.key_add()`                         |
| 显示名        | name 优先，否则 `"手机-" + uuid[:6]`                                         | `key_matcher._display_name()`                   |

### 3.2 对原对接文档的纠正（3 错 4 漏）

## 四、定稿复核发现的 3 处技术修正（v1.1 新增，必须遵守）

### 4.1 设备名：Android 不支持"自定义名字放进广播"

**问题**：`AdvertiseData.Builder` 只有 `setIncludeDeviceName(boolean)`，它放入的是**系统蓝牙名**  
（`BluetoothAdapter.getName()`）。**没有任何 API 能把任意字符串当作本地名放进广播**。  
所以"默认取系统名 + 去空格 + 接编号后缀"这套，**不改系统名就实现不了**。

**决策（修正 A8）**：

| 场景       | 行为                                                                                                         |
| -------- | ---------------------------------------------------------------------------------------------------------- |
| 默认（首次开启） | **不改系统名**，`setIncludeDeviceName(true)` 放 scan response，广播的就是系统蓝牙名（原样）                                      |
| 用户想带编号   | 页面「设备名」一行显示当前系统名 + 「改名」按钮 → 明确提示「会修改手机的整体蓝牙名称（配对其他设备时也会看到）」→ 同意后调 `BluetoothAdapter.setName("<原名去空格>-03")` |
| 用户想完全自定义 | 同上，走 `setName()`（受 OEM 限制时给出失败提示）                                                                          |
| 拒绝改名     | 名字通道用系统原名，UUID/Minor 仍然是编号，功能完整                                                                            |

> 影响面：`setName()` 是**全局副作用**（车载蓝牙、耳机配对列表都会变），所以必须显式确认一次，  
> 绝不静默改。这也是把 A8 从"自动接后缀"降级为"一键接后缀"的原因。

### 4.2 静默时段：直接沉睡（**已撤销运动安全阀**）

**问题**：D2 的静默 = SLOW 档停播。若用户 `21:00` 之后仍在骑行，手机在兜里、App 在后台、极空恰好没连上  
→ 停播 → 对端 75 秒后断电 → 行驶中失去动力。

**决策（用户 2026-11-18 拍板，最终）**：**不做运动检测安全阀**，静默期内直接沉睡。保持功能干净、无隐藏状态。

| 场景             | 静默期内的行为                       |
| -------------- | ----------------------------- |
| App 在前台        | **正常 250ms 广播**（活跃态压过静默）→ 车可用 |
| 极空已连接（BMS 在手边） | **正常 250ms 广播** → 车可用         |
| 后台 + 未连极空      | **停播（沉睡）** → 车不可用（对端 75 秒后断电） |

也就是说：**夜间要用车，就得让 App 在前台、或让极空连上**。这是明确的产品约定，不是 bug。

**必须配套的三件事**（把"安静失败"变成"用户知道"）：

1. **静默生效前 5 分钟提醒一次**（`quiet_notice_once`，可关）：  
   通知「`<起始时刻>` 起停止后台广播（省电）。夜间用车请打开 App 或用极空连接。」
2. **静默期的通知文案写清出路**：`钥匙 03 · 已暂停（时段静默）· 打开 App 或用极空连接可恢复`。
3. **页面状态行**（UI 第 9 项）显示「时段静默中（剩余 xx 小时）」，并提供「关闭静默」快捷入口。

> **已知取舍（用户明确接受）**：夜间骑行且恰好未连极空时会断电。缓解手段是上表三条提示，  
> 以及"把静默时段设短 / 关掉静默"这两个用户可操作项。**不做自动检测、不做轮询、不引入传感器。**

#### 4.2.1 已否决的方案（备查，不再实现）

| 方案                                        | 否决理由                                                                                                                               |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `TYPE_SIGNIFICANT_MOTION` 哨兵 + 10 分钟滑动倒计时 | **实现复杂度不划算**：需处理"触发后自动注销必须立刻重挂"、"边沿触发在已在运动中时不保证触发"（还需 2 秒加速度采样补判）、"静止计时自己数"、"Doze 推迟"四件事；任何一个写错都变成难查的静默失效。收益只是覆盖"夜间骑行且极空未连"这一个边缘场景 |
| 15 分钟定时轮询加速度                              | 有 12 分钟盲区（对端 75 秒就断电），且要反复唤醒 CPU，比沉睡更费电                                                                                            |
| 持续监听加速度计                                  | 毫安级，比广播本身还耗电                                                                                                                       |


**结论**：宁可让这个边缘场景"可预期地不可用 + 明确告知用户"，也不引入一个易错的状态机。  
如果将来确实出现"夜间经常要用车"的实际需求，正确解法是**调整/关闭静默时段**，而不是加传感器。

> 另：静默时段的起止建议保持"跨午夜"能力（默认 `21:00–05:00`），因为对端 24 小时扫描（§3.3），  
> 静默纯粹是手机侧省电，与对端无关。

### 4.3 首次编号必须由用户设定，不能给默认值

**问题**：若默认 `01`，两台新手机开箱都变 `01` = 同一把钥匙（A1c 的撞号场景必现）。

**决策**：`number` 初始为**空**；打开总开关时若为空 → 弹编号输入（`00`~`99`，默认预填一个  
"本机未占用的建议值"仅作提示、不自动采用）→ 未填不允许开播，通知文案「未设置编号，点击设置」。

## 五、广播报文（逐字节）

### 5.1 主包（advertising data，30 / 31 字节）

```
02 01 06                                                          ← Flags（系统自动加，不可关）
1A FF 4C 00 02 15 <UUID 16B> <Major 2B> <Minor 2B> <TxPower 1B>     ← 厂商数据 27 字节
             └ 公司 ID 0x004C（小端）  └ 02=类型, 15=后续 21 字节
```

- `1A` = 26 = 1(type) + 2(company) + 23(payload)，满足对端 `len ≥ 21`。
- `addManufacturerData(0x004C, payload)` 的 **payload 从 `02 15` 开始，不含公司 ID**（Android 自动补）。
- 构建参数（一条都不能少）：

| 设置                              | 值                         | 不设的后果              |
| ------------------------------- | ------------------------- | ------------------ |
| `setAdvertiseMode`              | `ADVERTISE_MODE_BALANCED` | —                  |
| `setTxPowerLevel`               | 用户档位（默认 MEDIUM）           | —                  |
| `setConnectable(false)`         | 不可连接                      | 变可连接广播，不符合 iBeacon |
| `setTimeout(0)`                 | 无限期                       | 默认非 0 会自动停         |
| `setIncludeDeviceName(false)`   | 主包不带名                     | 超 31 字节            |
| `setIncludeTxPowerLevel(false)` | 主包不带 TxPower              | 超 31 字节（33）        |

> **legacy 广播的正确保证方式**（P0 实证修正）：不要 `setLegacyMode` —— `AdvertiseSettings.Builder` 没有这个方法  
> （`javap` 实证：只有 `setAdvertiseMode / setConnectable / setDiscoverable / setTimeout / setTxPowerLevel`）。  
> 只要**不调用** `startAdvertisingSet(AdvertisingSetParameters, ...)`，`startAdvertising` 这条老 API  
> 产出的必然是 legacy PDU（31 字节上限）。扩展广播那套对端 MicroPython 解不出，故永久禁用。

### 5.2 扫描响应包（scan response）

```kotlin
advertiser.startAdvertising(settings, advertiseData, scanResponseData, callback)
```

- 内容仅 `setIncludeDeviceName(true)`（系统蓝牙名），正文 ≤29 字节；
- 对端是主动扫描，会收到 SCAN_RSP 帧并 `parse_local_name()` → name 这条 OR 通道生效；
- 名字与 UUID 都可被伪造，**不构成额外防护**。

## 六、身份与编号

```
前缀     = 627269646765000000000000000000    ← 12 字符 "bridge" 的 ASCII hex + 18 个 0（共 30）
编号 03  = 前缀 + "03"
完整     = 62726964676500000000000000000003    ← 32 字符
```

- 前缀可在「高级」改（改 = 换钥匙，对端须重新登记）。
- 编号：文本框 + 自动补零；同时写入 **Minor**；范围 `00`~`99`；首启必填（§4.3）。
- Major 固定 `0001`；Measured Power 固定 `0xC5`(-59)。
- 改编号 / 前缀 / 名字 / 功率 / 时段 → 若正在播，**立即停-启重建**；对端会在 2~4 秒内重新判近  
  （60 秒断电延时足够吸收这次中断，不会导致断电）。
- SharedPreferences 参与 `allowBackup`，换机恢复后可能两台手机同号 → 页面在改编号处提示一次。

## 七、生命周期状态机（B8=② + D2）

### 7.1 输入

| 符号   | 含义                            | 来源                                 |
| ---- | ----------------------------- | ---------------------------------- |
| `E`  | 总开关                           | `BleKeyPrefs.enabled`              |
| `N`  | 编号已设置                         | `BleKeyPrefs.number != null`       |
| `BT` | 蓝牙开 + 有 `BLUETOOTH_ADVERTISE` | `BluetoothAdapter.isEnabled` + 权限  |
| `F`  | App 有 started Activity        | 自建 `ActivityLifecycleCallbacks` 计数 |
| `K`  | 极空已连接                         | `JikongBleClient.connected`（巡检时读取） |
| `G`  | 距最后一次 `active` 的时长            | 服务内时间戳                             |
| `W`  | 当前落在静默时段（`21:00–05:00`，支持跨午夜） | `BleKeyPrefs`                      |
| `B`  | **亮屏提速窗口内**（最后一次亮屏后 ≤2 分钟） | `ACTION_SCREEN_ON` → `boostUntil`（v0.3.004） |

|              |   |     |
| ------------ | - | --- |
| \`active = F |   | K\` |

### 7.2 迁移表

| 当前              | 条件                    | 目标                | 动作                                   |
| --------------- | --------------------- | ----------------- | ------------------------------------ |
| 任意              | `!E \|\| !BT \|\| !N` | **STOPPED**       | 停播；通知文案说明原因（未设编号 / 蓝牙未开）             |
| STOPPED         | `E && BT && N`        | 按下列规则             | 开播                                   |
| **FAST**(250ms) | `active`              | FAST              | 刷新 `G` 时间戳                           |
| FAST            | `!active && G ≤ 5min` | FAST              | 宽限期不降档（人刚下车/刚要上车）                    |
| FAST            | `!active && G > 5min` | **SLOW**(1000ms)  | 停 → 以 1000ms 重启                      |
| SLOW            | `active`              | **FAST**          | 停 → 以 250ms 重启                       |
| SLOW            | `!active && W`        | **STOPPED（静默沉睡）** | 停播；通知「已暂停 · 时段静默 · 打开 App 或用极空连接可恢复」 |
| STOPPED(静默)     | `active` 或 `!W`       | FAST / SLOW       | 立即恢复（`active`→FAST，`!W` 且无活跃→SLOW）   |
| **任意在播态**       | **`B`（亮屏后 2 分钟内）**   | **BOOST**(100ms)  | 停 → 以 100ms 重启；通知原因「亮屏提速（100ms）· 剩 x 分 y 秒」 |
| **BOOST**(100ms) | **`!B`**              | 按 `active/G/W` 回落 | 走正常判定：`active`→FAST、静默→停播、否则→SLOW            |
| **BOOST**(100ms) | **再次亮屏**             | BOOST             | 窗口重置为 2 分钟；**mode 未变 → 不重建会话**            |

### 7.3 四条硬规则

1. **永不自动停**：除总开关、蓝牙关闭、静默时段（且无运动）外，后台永远以 SLOW 保底在播。  
   这是"走到车边就能解锁"的底线。
2. **静默优先级最低**：活跃态（前台 / 极空已连接）永远压过静默；静默只吃掉"后台慢速待机"那部分电。
3. **冷启动**（开机 / 被杀重建）无活跃条件时直接进 SLOW，不走 5 分钟宽限。
4. **极空连接不做快速订阅**：SLOW 档也一直在播，`K` 只影响"判近 3 秒 vs 6 秒"，不影响"能不能解锁"，  
   所以 60 秒巡检时读一次 boolean 即可，**不给 `JikongBleClient` 加观察者**（零耦合）。
5. **亮屏提速优先级最高**（v0.3.004）：`B` 压过 `active` 与 `W`——夜里亮屏就说明要用车，  
   不能因为"落在静默时段"而拒绝提速。提速**只改 advertiseMode**，不改任何判定依据。  
   灭屏**不缩短**窗口（覆盖"灭屏后揣兜走两步"）；窗口到期用 `postDelayed` 精确触发，不靠 60 秒巡检。

### 7.4 慢速档会不会被误判失联（已核算）

`loss_timeout_s = 15` 要求每 15 秒至少 1 帧。1000ms 广播 × 对端 25% 窗口 → 平均 4 秒一帧，  
15 秒内期望 3.75 帧，纯泊松 P(0) ≈ 2.4%；但**对端一命中任何一帧就升快档（60% 占空比，持续 10 秒）**，  
实际"连续 15 秒零帧"概率远低于此；且判 FAR 也要**持续 60 秒**才断电，中间任何一帧命中即回 NEAR。  
→ 慢速档安全，**不需要**为它调 `loss_timeout_s`。

### 7.5 亮屏提速的收益与代价（v0.3.004）

**为什么加**：真机体感"后台 1000ms 时走近要 8 秒"。对端不能动（它也要省电：基档只跑 25%
占空比、`hit_frames=3`），所以只能用手机侧的"亮屏"当免费的「人来了」信号。

**延迟推算**（对端保持基档「中」25%、`hit_frames=3`）：

| 阶段 | 计算 | 耗时 |
|---|---|---|
| 首帧（100ms 广播 ÷ 25% 占空比） | 100 ÷ 0.25 | 0.4 s |
| 剩余 2 帧（首帧后对端升快档 60%） | 100 ÷ 0.6 × 2 | 0.33 s |
| 对端升档生效（等本轮扫描结束，`scan_cycle_ms=2000`） | 0~2 s，平均 1 s | 1 s |
| **合计** | | **≈1.2~1.8 s（现状 8 s）** |

**参数对照**（Android 只有三档，不能自定义毫秒）：

| `ADVERTISE_MODE_*` | 标称间隔 | 我们用于 |
|---|---|---|
| `LOW_POWER` | 1000 ms | 后台保底（SLOW） |
| `BALANCED` | 250 ms | 前台 / 极空 / 宽限（FAST） |
| `LOW_LATENCY` | 100 ms | **亮屏提速（BOOST）** |

> 想设 500ms 做不到——`AdvertiseSettings` 只有这三个常量。能自定义间隔的
> `AdvertisingSetParameters.setInterval()` 属于 BLE 5.0 扩展广播，对端解析的是 legacy PDU，**不能用**。

**能耗**（4500 mAh 电池；100ms≈1.0 mA、1000ms≈0.1 mA，均取保守上限）：

| 亮屏次数/天 | 每次 2 分钟 | 额外耗电 | 占电池 |
|---|---|---|---|
| 50 | 1.7 小时 | 1.5 mAh | 0.03% |
| 100 | 3.3 小时 | 3.0 mAh | **0.07%** |
| 200 | 6.7 小时 | 6.0 mAh | 0.13% |

换算：最激进的 200 次/天也只相当于**亮屏 1 分钟**。所以这条功能不需要为电做取舍。

## 八、静默失效自愈（B6）

### 8.1 会静默失效的四类原因

下列情况 `AdvertiseCallback` **不回调失败**、日志干净、用户以为在播：

1. 别的 App 抢占 advertiser set（系统级上限）；
2. ROM 省电策略清掉广播集；
3. 蓝牙状态机抖动 / 协议栈重启；
4. 我们的 `BluetoothLeAdvertiser` 对象被 GC（未持强引用）；
5. **蓝牙关 → 开**：底层会话已被系统丢弃，但我们这边的状态可能还停在 `ADVERTISING`
   （`onStartFailure` 不会为"被外部关掉"而回调）。

### 8.2 断电门推导（为什么必须是 60 秒）

| 阶段              | 阈值         | 源码                       |
| --------------- | ---------- | ------------------------ |
| 停播 → 无帧 → 判 FAR | **15 秒**   | `loss_timeout_s = 15`    |
| FAR 持续 → 断电     | **60 秒**   | `power_off_delay_s = 60` |
| **停播 → 断电**     | **约 75 秒** | —                        |

| 巡检周期     | 最坏静默                       | 能否在断电前救回        |
| -------- | -------------------------- | --------------- |
| 15 分钟    | 900 秒                      | 不能（行驶中断电 15 分钟） |
| 5 分钟     | 300 秒                      | 不能              |
| **60 秒** | **~64 秒**（含重建 + 3 帧回 NEAR） | **能，余量 11 秒**   |

### 8.3 实际机制：**用「重新提交」代替「查询」**（v0.3.007 修正，必读）

**先说一个必须承认的事实**：Android **没有任何 API 能查询「广播当前是否真的在发」**。
`BluetoothLeAdvertiser` 没有 getter；`AdvertiseCallback.onStartSuccess` 只代表
「控制器接受了参数」，不代表空中已在发包。

而 v0.3.006 及以前的实现更糟：`BleKeyBroadcaster.start()` 在提交请求后**乐观置位**
`_state = ADVERTISING`（`BleKeyBroadcaster.kt:184`）。于是巡检判据
`expectedAlready && !isAdvertising()` 在「期望在播 + 实际已被停掉」时**恒为 false**
→ 永远不会重建，`巡检修复` 恒为 0。**那一版是空转，不是自愈。**

v0.3.007 改为两层：

| 层 | 做法 | 覆盖 |
|---|---|---|
| **事件驱动** | 蓝牙 `STATE_ON`、总开关、前后台、亮灭屏、静默边界 → 重算；其中**蓝牙 `STATE_ON` 直接强制重建** | 绝大多数 |
| **周期巡检** | **每 60 秒无条件 `stop → start`**（不再看 `isAdvertising()`） | ROM 静默停播 / 会话被丢弃 |

**为什么「无条件重建」是对的**：

- 重新提交是**唯一**能让控制器重新装载广播参数的动作，等价于「查询 + 修复」；
- 空窗 30~100 ms ≪ 对端 15 秒失联门 → 对端完全无感；
- 60 秒周期保证在 75 秒断电门内救回（见 §8.2）；
- 开销：每次约 5 条 HCI 命令、~50 ms、~5 mA → 1440 次/天 ≈ **0.1 mAh ≈ 0.002%/天**。

**两个必需的配套细节**（漏了就会出现新问题）：

1. **`advertisingSince` 不能重置**：例行重建会重复触发 `onAdvertisingStarted()`，
   若每次都写时间戳，「已播时长」会永远显示 0~60 秒。
   → 只在「从没在播 → 开始播」时记录起点（`BleKeyRuntime.onAdvertisingStarted()`）。
2. **通知必须去重**：例行重建若每次都 `notify()`，等于一天刷新通知栏 1440 次。
   → 只在「档位 / 错误 / 倒计时分钟」变化时刷新；UI 侧状态仍然每次更新。

> **诚实的边界**：即使这样做，「通知说广播中」仍然不等于「一定在发包」。
> 真正的权威只有两个：**ESP32 侧 `SCAN` 能收到**，或 `adb shell dumpsys bluetooth_manager`
> 里的 advertising 记录（且部分 ROM 如 OnePlus 9 Pro 的 dumpsys 根本不输出该段，实测只有 403 行）。
> 手机侧能做的极限就是「周期重新提交 + 状态如实体现在 UI 上」。

### 11.1 高级（折叠）

前缀编辑、静默时段起止与开关、设备名改名。

### 11.2 安全提示文案（定稿）

> 这把钥匙就是上面那串 32 位 UUID 的复制品：广播是公开的，任何人读到它、用另一台手机播出同样的 UUID，  
> 就能被车当作钥匙。**本功能防的是"忘带钥匙"，不防"有人偷车"。** 请勿把 UUID 截图外发。

### 11.3 设备名（A8 的落地形态）

**Android 没有「把任意字符串写进广播」的 API**：`AdvertiseData.Builder` 只有
`setIncludeDeviceName(boolean)`，它塞进 scan response 的是 **`BluetoothAdapter.getName()`**
（系统蓝牙名）。所以「系统名去空格 + 编号后缀」这个决策，只能通过**改系统名**实现。

落地（详情页「设备名」卡片）：

| 项 | 行为 |
|---|---|
| 默认 | **不动系统名**。广播的就是手机原名，功能完整（对端按 UUID 认钥匙，名字只用于看） |
| 显示 | 当前系统蓝牙名（无权限 / 蓝牙关 → 「读取失败」，不崩） |
| 「按编号改名」 | 建议名 = 系统名去空格 + `-NN`（如 `OPPOReno9-03`），**先弹确认框**写明「会修改手机整体蓝牙名，已配对的耳机/车载都会看到新名字」，确认后才 `setName()` |
| 长度 | 建议 ≤20 字符；超长只会在广播里被截断，**不影响匹配** |

**为什么不静默改**：`setName()` 是全局副作用（配对记录、车载显示都会变），
用户没预期的事情不能替用户做主。

### 11.5 自检为什么"扫不到自己"（v0.3.006 修正，必读）

**真机实测（2026-11-18 14:10，用户报告）**：自检报「5 秒内没扫到自己」，但同一时刻
ESP32 一直在扫到这台手机、且车处于通电状态 → **广播完全正常，是自检的判断前提错了**。

**根因：BLE 单天线分时收发，controller 通常不上报自己发出的包**（own-address filter）。
Android 没有 API 可以关闭该过滤，也没有 API 能回读"当前空中真的在发什么"
（`AdvertiseCallback.onStartSuccess` 只表示"控制器接受了参数"，不证明包已发出）。
→ **"扫不到自己"是多数机型的正常行为，不是故障。**

**因此自检的定位从"验证广播"改为"分层诊断扫描链路"**：

| 结论 | 触发条件 | 含义 | UI 颜色 |
|---|---|---|---|
| `SELF_FOUND` | 收到自己的 UUID | **强证据**：确实在播且格式正确 | 主色（唯一"通过"） |
| `NO_SELF_SCAN_OK` | 收到别的 iBeacon，无自己 | 扫描 + Apple 厂商数据解析都正常，纯属机型不上报自发包 | 中性 |
| `NO_SELF_NO_BEACON` | 只收到别的 BLE 设备 | 扫描正常但附近无信标，无从比对 | 中性 |
| `NOTHING_SEEN` | 5 秒零包 | **无法判断**：可能被其他扫描占用（极空扫描页），也可能附近确实没有 BLE 设备 | 中性 |
| `FAILED` | 权限 / 蓝牙关 / 不支持 / 异常 | 根本没扫成 | 错误色 |

**文案红线**：
- 不许把 `NO_SELF_*` / `NOTHING_SEEN` 写成"失败"，不许出现"距离太远/遮挡太强"——自己扫自己没有距离概念；
- **唯一允许用错误色的只有 `FAILED`**。手机侧本就无法自证广播，红色只会制造误报；
- `NOTHING_SEEN` 只能说"无法判断"，并提示"若你确定附近有蓝牙设备仍为 0，才是扫描被占用/受限"——
  因为静室里一台 BLE 设备都没有是完全可能的。

**顺带修掉的两个实现缺陷**（同一处代码）：

| # | 缺陷 | 后果 | 修法 |
|---|---|---|---|
| 1 | `onScanResult` 命中后直接 `finish()` → `onDone()` 在 **binder 线程**回调 | 在非主线程写 Compose 状态，可能不刷新或抛异常 | 统一 `handler.post { onDone(res) }` |
| 2 | `hits` 是普通局部变量，binder 线程写、主线程读 | 缺少可见性保证，超时判定可能读不到 | 改 `AtomicInteger` + `ConcurrentHashMap.newKeySet()` |

> **一句话**：手机侧没有任何手段能证明"包真的在空中"，唯一权威永远是 **ESP32 侧 `SCAN`**。
> 自检的价值只在于——**扫不到时，帮你分清是本机硬件限制还是扫描链路坏了**。

## 十三、功耗

| 档位               | 间隔      | 净增量（4000mAh）  | 判近延迟    |
| ---------------- | ------- | ------------- | ------- |
| LOW_LATENCY      | ~100ms  | 1.5~4 %/天     | 1.5~2 秒 |

| LOW_POWER（慢速保底）  | ~1000ms | 0.2~0.7 %/天   | 6~7 秒   |

- 成本 = 控制器周期唤醒 + 每包三通道（37/38/39）射频脉冲。**不持 WakeLock、不阻止 Doze、CPU 可忽略**——  
  与 VNT / WebSocket 长连接（持续占射频 / 心跳）性质不同。
- **判据**：净增量 ≤2 %/天；>2% 先改生命周期，再考虑降档。
- **调间隔是线性小账，改生命周期是结构性大账**：24h 常驻 vs 只在活跃时段 250ms 差 10 倍。  
  省电优先级：① 活跃/慢速分层 → ② 静默时段 → ③ 降功率 → ④ 最后才降间隔。
- 实测：`dumpsys batterystats --reset` → 固定一种策略用 24h → `dumpsys batterystats` 取本 UID  
  `Estimated power use` → 与"开关关闭 24h 基线"相减得净增量；另看"息屏 8 小时掉电"，
  > 3% 说明控制器唤醒过频，该降档。

### 14.1 命令

```bash
CONFIG                                          # 开机 10 秒窗口内进入配置模式

KEY ADD 手机-小张 - 62726964676500000000000000000003

```

### 14.2 「手打」到底指哪（G2 结论 · 2026-11-18 12:20 校正）

- **Qt 工具**（`tools/serial_monitor_qt.py`）：全是按钮，**没有自由输入框**；「设为钥匙」会自动拼出  
  `KEY ADD <名字> <MAC> <UUID>`。它省掉了手打 32 位 UUID 的风险，但**名字这条路径它同样会错**  
  （见下方「路径 B」）——所以「用工具就不会出错」这句 v1.3 的说法**已作废**。
- **手打** = 板子进入配置模式后，用**任意串口终端**（REPL / 串口助手 / PuTTY / mpremote）直接敲命令。

**两条都会静默失败（不报错、但永远匹配不上）的路径**：

| 路径 | 写法 | 结果 |
|---|---|---|
| **A：`-` 占位** | `KEY ADD 手机-小张 - <uuid>` | `-` 被原样存成 `mac="-"`，**第二台手机再传 `-` 会覆盖第一台** |
| **B：名字含空格** | 工具自动拼 `KEY ADD OPPO Reno9 <mac> <uuid>`，或手打 `KEY ADD 手机 小 张 - <uuid>` | `split()` 后字段整体错位 → 名称只剩 `OPPO`、MAC 变成 `Reno9`、UUID 变成真实 MAC |

> **路径 B 为什么是高频必踩**：手机广播名 = 系统蓝牙名（Android 无自定义名 API，§11.3），
> 而 `OPPO Reno9` / `HUAWEI Mate 40` / `Redmi Note 12` 这类出厂名**都带空格**。
> 工具只打印「已发送添加钥匙命令」，用户以为成功，到车边却不通电。
> **规避**：登记前先在详情页「设备名 → 按编号改名」（去空格 + `-NN` 后缀）；
> 根治见要求单**第 19 条**（参数个数校验 + 名称空白校验 + 工具侧自动替换）。

> **⚠ 2026-11-18 实测更正（推翻本文档 v1.2 早前说法）**：`-` 不是"空占位"，它会被  
> `config_mode.py:302` 原样写成 `mac="-"`。于是**第二台手机也用 `-` 时，`key_add` 的去重条件  
> `mac 相同` 命中（`"-" == "-"`）→ 第二台静默覆盖第一台**，无任何报错。  
> 因此多手机场景的正确做法是：
>
> 1. **优先用 Qt 工具**（它传扫描到的真实 MAC，不存在路径 A），但**必须确认名字无空格**（路径 B）；
> 2. 必须手打时，**每台不同名字**，且**先 `KEY LIST` 留底再 `ADD`**，加完立刻 `KEY LIST` 复核把数对不对；
> 3. 上述两条缺陷与其余改造项已整理成**修改要求单**（**19 条**）：  
>    `docs/research/espauto-unlock-change-request.md`。

### 14.3 其他注意

- `KEY ADD` 只写 `config.json`（`keys` + 同步旧字段 `key_names`/`key_macs`）；`main.py` 有 `keys` 优先 `keys`。  
  操作前备份 `config.json`（`tools/backup_device.py`），改后 `KEY LIST` 复核。
- **改/删钥匙的安全流程**（因对端无编辑命令、无删除按钮、重名会静默覆盖）：  
  `KEY LIST` 抄下现有三元组 → `KEY DEL <旧名>` → `KEY ADD <新名> <mac> <uuid>` → 再 `KEY LIST` 核对把数不变。
- **钥匙数上限 10 把**，超限只打串口 warn、工具无提示（`config_mode.py:123-125`）→ 加完务必 `KEY LIST` 看总数。
- 对端匹配是 `name OR mac OR uuid` 三路 OR，**名字本身就是一把钥匙**  
  （`key_matcher.py:134-146`）→ 广播名必须带唯一后缀（本设计默认「系统名去空格 + `-编号`」），  
  绝不使用 `OPPOReno9` 这类出厂名。
- **★ 已知未修漏洞（对端侧）**：手环这类「只有名字」的记录，同型号设备靠近即可通电  
  （现役荣耀手环 3 广播名 `honor Band 3-042`，后缀来自 MAC 尾号，仍有千分之一撞名概率；  
  换成 `Mi Smart Band 4` 这类无后缀出厂名则同型号全部互通）。**我方无法在客户端规避**，  
  已写进 `espauto-unlock-change-request.md` 第 11 条：要求名字彻底退出匹配、手环改按 MAC；
  旧「仅名字」数据由对端**升级时手工改一次 `config.json`**（明确要求不加运行时检测，开发板省内存）。
  在第 11 条落地前，**这是已知风险，不是已解决项**。
- 阈值**当前不改**：`rssi_on = -80`、`rssi_off = -90`。手机塞裤兜 RSSI 常 -65~-80；
  若"贴车仍不判近"→ 放宽到 -75；若"隔 10 米就通电"→ 收紧并保持 ≥10dB 滞后。
- **★ 阈值全局共享是已知缺陷**（`config.py:29-30` → `main.py:95-103` 单值传入，
  `key_matcher.py:65/70` 逐帧套用）：手环（0 dBm，贴腕）与手机（+1 dBm，裤兜衰减 10~15 dB）
  用同一对阈值，必然一侧吃亏。要求单第 17 条：**每把钥匙可带 `rssi_on`/`rssi_off`，未设回落全局**，
  `KEY SET <名> rssi_on=.. rssi_off=..` 可调。
- **★ 多设备会互相踩**（`main.py:289` 显示 `last_key_name`=最后一帧的钥匙；状态机只有一份）：
  ①一把走远就会整体判 FAR 断电，哪怕另一把贴车；②界面几乎总显示帧率高的手机（4 帧/秒 vs 手环 2~3）。
  要求单第 18 条：**任一近即通电、全部远离才断电**；显示**触发通电的那把**并带 RSSI。

## 二十、运行观测与日志判读（v1.8 新增 · v0.3.008）

### 20.1 为什么不做「逐项手测」

验收单 50 项，逐项点不现实，且多数项（「后台 8 小时后还能通电吗」「被 ROM 杀掉后多久复活」）
本质上只能靠**长时间挂机**而不是手点验证。所以判据改成：

> **挂着跑几天 → 在 App 里点「上传诊断日志」→ 看 `[BleKeySummary]` 一行 + 关键事件。**

日志链路（既有能力，不需新通道）：

```
Timber.xxx  →  DiagLogTree（BridgeApplication 里 plant）
            →  DiagLog（内存环形 600 条 + 磁盘 files/logs/bridge.log 5MB×5 轮转）
            →  设置 → 连接 →「上传诊断日志」→ POST /api/logs
            →  MySQL device_logs（按 device_id + ts + line_hash 去重）
            →  管理后台「日志」页按 tag 过滤：BleKeySummary / BleKeyService / BleKey / BleKeyHealth
```

### 20.2 补齐的 3 个盲区（改前只有事件流，没有结论）

| 盲区 | 改前表现 | 改后 |
|---|---|---|
| B1 生命周期 | `onCreate`/`onDestroy`/START_STICKY 重建**零日志** | `BleKeyHealth.onServiceCreate/onServiceDestroy` 记录创建次数 + **断档间隔**；`intent == null` 单独一条「服务被系统重建」 |
| B2 巡检结论 | 每轮只打「强制重建」，不知道成没成功 | 每轮 D 级心跳（档位 + 屏幕/Doze/省电 + 广播器状态）；**每 10 轮一条 I 级汇总**含累计失败数 |
| B3 系统压制 | 广播停了分不清是 ROM 压制还是我们不播 | 心跳带 `PowerManager.isInteractive / isDeviceIdleMode / isPowerSaveMode` |

### 20.3 健康台账（`BleKeyHealth`）字段

SharedPreferences `blekey_health`，每 60 秒 `apply()` 一次（几字节，可忽略）：

| 键 | 含义 |
|---|---|
| `service_creates` | 服务创建累计次数 —— **越大说明被系统回收越频繁** |
| `watchdog_runs` | 巡检累计轮数（60 秒/轮，正常情况下 ≈ 挂机分钟数） |
| `adv_fails` | 广播启动失败累计次数 —— **唯一需要盯的红色指标** |
| `last_fail_reason` | 上次失败原因（原因变了才升 W 级） |
| `broadcast_ms` | 累计广播毫秒（按巡检**实际间隔**累加，单次钳到 3 分钟防关机灌水） |
| `mode_FAST/SLOW/BOOST/QUIET/BLOCKED` | 各档位累计轮数 —— 看档位分布 |
| `last_watchdog_at` | 最后巡检时刻 |
| `last_gap_ms` | 上次停机间隔（重建时算出，> 150 秒判「疑似被杀/重启」） |
| `last_destroy_reason` | 上次销毁原因（主动停止 / 被动回收） |

### 20.4 上传摘要行（第一眼结论）

`ConnectionViewModel.uploadLog()` 在 `DiagLog.dumpLines()` **之前**调
`BleKeyHealth.appendSummary(context)`，于是上传流最后多出这样一行：

```
[BleKeySummary] v0.3.008 钥匙=03 启用=是 功率=中（约 -7dBm，默认） 静默=21:00–05:00
| 服务创建=7次 巡检=4321次 最后巡检=11-18 15:30:00 失败=0次 累计广播=68小时12分
档位轮数=SLOW2980/FAST1100/QUIET241 上次断档=2分13秒 上次销毁=被动销毁 | 首次启用=11-15 09:12:03
```

判读口诀：

| 看什么 | 正常 | 异常信号 |
|---|---|---|
| `失败` | 0 | > 0 且持续增长 → 看 `BleKeyHealth` 的 W 级原因 |
| `巡检` ÷ 挂机分钟 | ≈ 1 | 明显偏小 → 服务被反复杀 / 手机重启 |
| `累计广播` | 接近挂机时长（除静默时段） | 远小于挂机时长 → 长期 BLOCKED 或静默配错 |
| `服务创建` | 个位数 | 几十次 → ROM 强烈回收，需查电池白名单 |
| `上次断档` | < 2 分钟 | 数小时 → 中间死过，配合 `last_destroy_reason` 判断 |

### 20.5 日志量核算（为什么要降噪）

改前：每 60 秒 3 条 I 级（强制重建 + 广播已停止 + 广播已启动）≈ **4320 条/天 ≈ 0.5 MB/天**，
磁盘 5 MB 与其他模块争抢，BleKey 自己就能吃掉大半缓冲。

改后（v0.3.008）：

| 项 | 改前 | 改后 |
|---|---|---|
| **BleKey 自己**每天条数 | ≈ 4320（全 I/部分 E） | ≈ 1584（1440 D + 144 I） |
| **BleKey 自己**每天字节 | ≈ 0.5 MB | ≈ 0.2 MB |
| 磁盘 6 MB 按 BleKey 单独算能留 | ≈ 12 天 | ≈ 30 天 |

> ★ **口径纠正（2026-11-18 17:05 实测）**：上面只是 BleKey 一个模块的量。
> `MAX_DUMP_LINES = 5000` 与磁盘 6 MB 是**全机所有模块共享**的，所以实际窗口要看全机总量。
> 实测生产机 `f2c38ebee251a196`（2026-11-13 ~ 11-17）：
>
> | tag | 占比 |
> |---|---|
> | 微信 | 28.1% |
> | 微信WS | 23.8% |
> | Bridge | 15.7% |
> | 组网 | 12.4% |
> | 相册 | 9.5% |
> | 监控 / JikongBle / 相册备份 / JkProximity / SSH / Jikong / 无界面模式 | 合计 < 8% |
>
> 每天总量 **3600 ~ 7500 行**（11-13 7474 / 11-15 363 / 11-16 5861 / 11-17 6302）。
> 因此：
> - **单次上传 5000 行 ≈ 覆盖最近 1 天**（不是 3 天）；
> - **服务端 20000 行/设备 ≈ 保留 3~4 天**（不是 12 天，也不是文档里说的 30 天——30 天是过期上限，条数上限先到）；
> - BleKey 日志约占全机 8%，降噪后已经不会挤掉别人，也没被别人挤爆。
>
> 结论：**建议每天点一次上传**（10 秒），不要攒到第 3 天——那时最早的已被客户端滚掉。

具体手法：
1. `BleKeyBroadcaster`：**例行重建**（force 且 UUID+档位都没变）把「已停止 + 已启动」两条 I 合并成一条 D；
2. 同一失败码连续出现只在第一次打 E，之后 D（失败次数由台账累计）；
3. 巡检常态 D 级、每 10 轮一条 I 级汇总。

> **D 级不上 Logcat，但仍写入磁盘与上传流** —— 所以「降噪」只影响 adb logcat 观感，
> 不影响事后追溯。这点是设计前提，改 `DiagLog` 时不要动。

### 20.6 三种取证方式（按场景选）

| 方式 | 命令/路径 | 适合 | 限制 |
|---|---|---|---|
| **上传日志**（推荐） | App 设置 → 连接 →「上传诊断日志」 | 已跑了几小时~几天，要回溯 | 只带最近 5000 行（**全机混合，≈1 天**）；需服务端可达 |
| ADB logcat | `adb logcat -s BridgeDiag:I` | 复现某个瞬间（开关蓝牙、亮灭屏） | 必须连得上；灭屏后无线 adb 易掉 |
| 直读磁盘文件 | `adb shell run-as my.bridge.com cat files/logs/bridge.log` | 上传失败时兜底 | 需 debug 包 |

### 20.7 自动清理：不需要任何手动删除

**结论：用户不需要做任何「定期清日志」操作。** 三层各自自动裁剪：

| 层 | 机制 | 上限 | 触发时机 | 代码位置 |
|---|---|---|---|---|
| 手机内存 | `ArrayDeque` 环形，满了 `removeFirst()` | 600 条 | 每条日志写入 | `DiagLog.append()` |
| 手机磁盘 | `bridge.log` 满 1MB → `.1`，`.1→.2`…`.4→.5`，删 `.5` | ≈**6MB**（主 + 5 滚动） | 主文件满 1MB | `DiagLog.rotate()` |
| 手机磁盘（启动兜底） | 删超出份数的残留 | — | `DiagLog.init()` | `cleanupExcess()` |
| 服务端 MySQL | 每次入库后 `DELETE ... OFFSET max_entries`（按 `ts DESC`） | **20000 行/设备** | **每次上传** | `LogStore.add()` |
| 服务端 MySQL（按天） | `DELETE WHERE ts < now - retention_days` | **30 天** | 每次上传后（每小时最多一次） | `_maybe_cleanup()` |

实测佐证（2026-11-18 17:05，生产库）：真机设备恰好 **20000 行**（11-13 15:53 ~ 11-17 18:11），
超龄（> 30 天）记录 **0 条** —— 两条清理都在正常工作。

**唯一会主动删除的动作**是管理后台「清除全部日志」按钮 → 下发 `clear_log` 命令 →
`DiagLog.clearAll()`（连磁盘文件一起删，防删库后又被重新上传回去）。平时不会自动触发。

**代价要理解清楚**：自动清理 = 旧日志被新日志挤掉，靠「磁盘 6MB / 服务端 20000 行」滚动。
想留住某段历史，就在那之前点一次上传；不想留也行，详情页「运行概况」的累计数字（服务创建、
巡检轮数、失败次数、累计广播）是**持久台账、永不被日志轮转影响**，那才是长期结论的载体。
