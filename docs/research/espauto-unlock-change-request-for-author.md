## 零、背景与范围

### 0.1 这条链路现在是怎么工作的

手机 App（Android，BLE peripheral）持续广播一条 **iBeacon**；本项目的 ESP32（central）扫描到后，
按 **UUID** 认定为钥匙，再用 RSSI 判近远，决定继电器通电/断电。

**已经跑通、不需要你重做的部分**（2026-11-18 实测确认）：

| 环节 | 状态 |
|---|---|
| 手机主包 iBeacon（company `0x004C`、`0215`、16 字节 UUID），设备名放 scan response | 正常 |
| `parse_ibeacon_uuid()`（`src/ble_scanner.py:71-95`）解出 32 字符小写无连字符 UUID | 正确 |
| `KEY ADD` 登记后 `SCAN` / `KEY LIST` 可见 | 正常 |
| 近远判定、迟滞、`loss_timeout_s`、`power_off_delay_s` | 按原设计工作 |

广播协议、扫描时序、点火逻辑**不在范围内，不要动**。

### 0.3 五条必须先读通的背景结论

这五条决定了后面每一条「为什么必须改」。如果其中某条你觉得不成立，请先就这一条回复，不要直接改代码。

**① 名字不是标签，是定位符，但绝不能是凭据。**
现状 `_find_key()` 是 `name OR mac OR uuid` 三路 OR。手机广播带设备名，而 `OPPOReno9` 这类
出厂名同型号几千万台完全相同 → **任何同款手机靠近都能通电**。所以第 11 条要求名字彻底退出匹配；
同时名字仍是 `KEY SET` / `KEY DEL` 的首选定位符，所以要**唯一**（第 6 条）。

**② 手环没有 UUID，但绝大多数有固定 MAC。**
BLE 手环普遍使用 **public static address**（地址固定，扫描即可拿到，如 `C8:47:8C:1A:2B:3C`），
你现在的登记流程本来就同时记录了 MAC。所以「名字退出匹配」不会砍掉手环能力——改按 MAC 即可。
只有极少数用 RPA（地址轮换）的设备不能当钥匙，这类设备**不得**回退到名字匹配。

**③ 手机的 BLE 地址是随机的，重建广播就变。**
所以任何「名字 + MAC」同时相等的判定，第二次开机就永久失效；`SCAN` 的设备列表也不能按 MAC 去重（第 14 条）。

**④ 手机广播的设备名 = 系统蓝牙名，改不了。**
Android 没有「把自定义字符串写进广播」的 API（`AdvertiseData.Builder` 只有
`setIncludeDeviceName(boolean)`）。所以典型出厂名**带空格**：`OPPO Reno9`、`HUAWEI Mate 40`、
`Redmi Note 12`。而你的工具拼命令是 `"KEY ADD %s %s %s" % (name, mac, uuid)` → 空格一多，字段全错位（第 19 条）。

**⑤ 这是 ESP32 开发板，RAM 极小——所有改动必须零额外常驻开销。**

| 做法 | 内存 | 结论 |
|---|---|---|
| 换掉 `_find_key` 的匹配顺序（第 11 条） | **0 字节**（同样的循环、同样的字段） | 采用 |
| 参数个数 / 名称空白校验（第 19 条） | **0 字节**（一次 `len()` + 一次 `in` 判断） | 采用 |
| 每钥匙运行状态（第 17/18 条） | 每把 4 个 int ≈ **16 B** × 10 = **160 B**；阈值 8 B × 10 = 80 B | 唯一允许的新增 |
| 启动时扫描白名单、打印停用告警 | 额外遍历 + 字符串拼接 | **不做** |
| 记录里加 `type` / `disabled` / `weak` 字段 | 每条 +几~十几字节 | **不做** |
| 旧数据兼容降级分支 | 多判断 + 分支代码 | **不做**（旧数据你升级时手工改一次 `config.json`） |

## 一、工具界面（`tools/serial_monitor_qt.py`）

### 1. 钥匙列表必须可编辑：加「改名」「删除」两个按钮

**要求**：`🔑 钥匙列表` 弹窗由只读报表改为可操作列表——底部在「关闭」左侧增加「改名」「删除」
两个按钮，作用于当前选中行；操作完成后**弹窗内列表自动刷新**，不需要用户关掉再打开。

**现状**（`serial_monitor_qt.py:742-791`）：

- 表格 `setEditTriggers(QTableWidget.NoEditTriggers)`（`:773`），不可编辑；
- 弹窗只有 `QPushButton("关闭")`（`:785`）；
- 全文只有两处 `KEY` 命令下发：`KEY ADD`（`:721`/`:723`）、`KEY LIST`（`:740`）——**无删除、无改名**。

**为什么必须改**：钥匙的唯一修改途径是手工编辑设备根目录的 `/config.json`。
该文件被 `main.py` 启动期读取，手改出错会导致配置读取失败，属于用户不该触碰的文件。

**实现要点**：

```python
row_btns = QHBoxLayout()
btn_rename = QPushButton("改名")
btn_del    = QPushButton("删除")
row_btns.addWidget(btn_rename); row_btns.addWidget(btn_del)
btn_rename.clicked.connect(lambda: self._rename_selected_key(table, keys))
btn_del.clicked.connect(lambda: self._delete_selected_key(table, keys))
```

- **改名**：`QInputDialog.getText` 预填当前名 → 发 `KEY SET <旧名> name=<新名>`（第 5 条）；
- **删除**：`QMessageBox.question` 二次确认，**弹窗文案必须含钥匙名与 UUID** → 发 `KEY DEL <名>`
  （第 9 条支持 UUID / 序号定位）；
- 两者完成 → 自动重发 `KEY LIST` 并重绘弹窗；
- 未选中行时两个按钮置灰（不要弹「请先选中」）；
- 弹窗默认 460×360，加两个按钮后请调整高度，避免表格被压缩到只剩两三行。

**验收**：不打开串口终端、不编辑 `config.json`，仅用工具即可完成「改名」与「删除」；
改完弹窗内立刻可见；重开弹窗仍正确。

### 2. 添加钥匙时必须一律弹出命名框

**要求**：`➕ 添加选中为钥匙` **无论设备是否有名字，一律弹出命名对话框**，
预填值按优先级取：`扫描到的设备名` → `"手机-" + UUID前6位` → `"钥匙"`。用户取消或留空则不添加。

**现状**（`serial_monitor_qt.py:703-717`）：只有设备名称为空时才弹窗，有名字就直接沿用：

```python
if uuid and not name:                      # ← 只有"无名字"才弹窗
    default_name = "手机-" + uuid[:6]
    text, ok = QInputDialog.getText(...)
```

**为什么必须改**：名字是 `KEY SET` / `KEY DEL` 的**首选定位符**（第 5、9 条），也是界面展示名。
而名字在登记瞬间被写死、之后只能靠工具改（第 1 条），登记时不给确认机会，就会留下一串改不掉的名字。
另外预填值还要做空格替换（第 19 条），这两条改在同一处。

**实现要点**：预填后用户按回车即可确认，手环场景只多一次回车，不改变原有习惯。

**验收**：选中带名字的设备点添加 → 必然弹出预填框；改成 `手机-03` 后 `KEY LIST` 显示 `手机-03`；
取消对话框 → 不新增任何记录。

### 3. 必须提供「删除钥匙」入口，并对「删到 0 把」高危确认

**要求**：删除入口并入第 1 条；另外对**删除最后一把钥匙**单独处理——允许删除，但必须弹出高危确认，
文案必须明确：

> 删除「手机-03」后钥匙列表为空，**车辆将不再自动通电**（任何人靠近都不会启动）。确定删除？

**现状**：固件有 `KEY DEL <name>`（`config_mode.py:131-138`），工具内无任何按钮触发。

**为什么必须改**：吊销一把钥匙是安全动作（手机丢失、换号、人员变更），
不应要求命令行或改配置文件。

**验收**：工具内可删任意一把；删到 0 把时出现高危确认；取消则不删。

### 4. 设备列表必须标注「已登记为钥匙」

**要求**：`SCAN` 设备列表增加第 5 列「钥匙」，已登记的显示 `✔`，未登记留空。

**现状**（`serial_monitor_qt.py:727-735`）：四列（名称/地址/RSSI/UUID）一次性 `setItem`，无状态列。

**为什么必须改**：重复添加是第 6 条覆盖问题的触发路径；用户无法判断「我是不是已经加过了」，
会出现「以为加了两把、实际只有一把」。

**实现要点**：

- 判定与固件**改造后**的匹配口径一致（第 11 条）：`uuid` 命中 → 已登记；否则 `mac` 命中 → 已登记；
- **`name` 命中不算已登记**（名字不再参与匹配，见第 11 条）；
- 数据复用 `_show_key_list()` 已收集的 `_key_list_data`，无需额外请求；
- 加列后同步调整列宽记忆的列索引（相关逻辑在 `:918-976`）。

**验收**：已登记的钥匙在设备列表带 `✔`；删除后重新 `SCAN`，标记消失；
仅同名但地址/UUID 都不匹配的设备**不带** `✔`。

## 二、固件数据正确性（`src/config_mode.py`）

### 5. 必须新增 `KEY SET` 命令（支持改名 / 改字段 / 清空字段）

**要求**：新增命令，其余命令保持不变：

```
KEY SET <定位符> [name=<新名>] [mac=<新mac>] [uuid=<新uuid>]
```

**语义（逐条不可改）**：

| 项 | 规定 |
|---|---|
| 定位符解析顺序 | ① 名称精确匹配 → ② UUID（归一化后）匹配 → ③ `KEY LIST` 的 1-based 序号 |
| 只更新什么 | 仅更新命令中**显式出现**的字段，未出现的字段不动 |
| 显式空值 | `mac=` / `uuid=` 传空 → **清空该字段**（解决第 8 条） |
| 命中多条 | **报错并列出全部候选**（`名称重复，请改用 UUID 或序号：1. … 2. …`），不猜 |
| 未命中 | 报错 `未找到钥匙: <定位符>`，**不新增**（`SET` 绝不退化为 `ADD`） |
| 成功输出 | 打印改后的完整三元组 `名称=… 地址=… UUID=…` |

**现状**：命令集只有 `KEY LIST` / `KEY ADD` / `KEY DEL`
（`config_mode.py:295-310`，帮助文本 `:5`/`:326`/`:335`）。

**为什么必须改**：没有 `SET`，任何编辑都退化为「先 `DEL` 再 `ADD`」。中间态里这把钥匙**不存在**——
若此时人已在车上、车已通电，`_find_key` 找不到钥匙 → 15 秒判 FAR → 60 秒后断电。
**改一次钥匙 = 一次潜在断电。**

**实现要点**：

- 在 `_handle_cmd()` 内新增 `sub == "SET"` 分支；`cmd.split()`（`:288`）后再拆 `k=v`，`name` 值不允许含空格；
- 复用 `_load_keys()` / `_save_keys()`，写盘后保持旧字段 `key_names`/`key_macs` 同步（`:90-91` 现有逻辑不动）。

**验收**：

- `KEY SET 手机-03 name=手机-A` → `KEY LIST` 显示 `手机-A`，UUID 不变；
- `KEY SET 手机-03 mac=` → 该行地址列为空，UUID 不变；
- `KEY SET 不存在的名字 name=x` → 只报错，钥匙总数不变。

### 6. `KEY ADD` 改为「只新增」，重名/重复必须拒绝而不是覆盖

**要求**：`KEY ADD` 命中已有记录时**一律拒绝并报错**，禁止静默覆盖；更新统一走 `KEY SET`（第 5 条）。

**拒绝口径（三种，文案必须区分）**：

| 冲突 | 报错文案 |
|---|---|
| 名称已存在 | `名称已存在：手机。请换一个名字，或使用 KEY SET 改名。` |
| UUID 已登记 | `该 UUID 已登记为「手机-03」，无需重复添加。` |
| MAC 已登记 | `该地址已登记为「手环-老王」，无需重复添加。` |

**现状**（`:110-122`）：

```python
for k in keys:
    if (k.get("name") == name or (mac and k.get("mac") == mac)
            or (uuid and k.get("uuid") == uuid)):
        k["name"] = name            # ← 名字被后加的覆盖
        ...
        _log.info("钥匙已更新: ...")  # ← 只报"更新"，用户以为加了新的
```

**为什么必须改**：两台手机都叫 `手机` 时，第二台直接把第一台覆盖，日志写「钥匙已更新」，
`KEY LIST` 仍然 1 把。用户以为登记了两台，实际只有一台能通电——**静默数据丢失**，
且表现为「偶发不解锁」，几乎无法排查。

**验收**：连续添加两台同名手机 → 第二次明确报「名称已存在」；`KEY LIST` 仍是 1 把且**未被修改**；
改成不同名字后添加成功，变 2 把。

**名字唯一是硬约束，不接受例外**（请照此实现，不要加「同名但 UUID 不同就放行」的分支）：

- 判定只比较**名称字符串**，**与 mac / uuid 是否相同无关**。第一台叫 `手机一`，第二台也叫 `手机一`
  但 mac、uuid 全都不同 → **照样拒绝**；
- 同一台设备重复添加（UUID 相同、名称也相同）→ 同样拒绝，提示「该 UUID 已登记为…」；要改就 `KEY SET`；
- 同一个人有两台设备（手机 + 手环）→ 必须区分命名：`手机一-手机`、`手机一-手环`。
  这是本约束的既定代价，**不允许为了让它们同名而放宽**。

**为什么名字必须唯一**：名称同时是 `KEY SET`（第 5 条）和 `KEY DEL`（第 9 条）的**首选定位符**。
一旦允许同名，这两条命令的「按名字找」就会指向多行，只能退化成「报错让用户改用 UUID」，
那等于把定位符能力废掉，且历史上已经产生重名数据（见第 9 条候选列表）。
**宁可要求用户多打四个字，也不让命令产生歧义。**

### 7. `-` 占位必须归一化为空，且空字段不参与去重

**要求**：`KEY ADD` / `KEY SET` 解析时，把 `-`、`_`、`none`、`null`（不区分大小写）统一归一化为**空字符串**：

```python
def _norm(v):
    return "" if (v or "").strip().lower() in ("-", "_", "none", "null") else (v or "").strip()
mac, uuid = _norm(mac), _norm(uuid)
```

并且：**空字段一律不参与去重比较**（第 6 条的三种冲突判定里，空值跳过）。

**新增硬校验（防止产生永远匹配不上的死记录）**：

- `name`、`mac`、`uuid` **三者全空** → 拒绝：`名称、地址、UUID 不能全为空`；
- **`mac` 与 `uuid` 同时为空**（只给了名字）→ 拒绝：
  `仅有名称无法作为钥匙。请提供地址或 UUID：KEY ADD <名称> <MAC>`。

**现状**：`-` 被原样存成 `mac="-"`（`:302` `mac = parts[3]`，无校验）。
于是第二台手机同样传 `-` 时，去重条件 `mac 相同` 命中（`"-" == "-"`）→ **第二台覆盖第一台**。

**为什么必须改**：手机钥匙的正确用法就是「没有固定 MAC」（Android 随机地址），
所以**每台手机都会走 `-`**——这是必踩路径，不是边缘情况。
而只给名字的记录在第 11 条之后永远匹配不上，属于必被拒绝的无效配置。

**验收**：

- `KEY ADD 手机-03 - <uuidA>`、`KEY ADD 手机-04 - <uuidB>` → `KEY LIST` **两把**，地址列均为空，互不覆盖；
- `KEY ADD 空钥匙 - -` → 拒绝并报错；
- `KEY ADD 只有名字 - -` → 拒绝并提示「仅有名称无法作为钥匙」。

### 8. 已设字段必须可清空

**要求**：`KEY SET` 的 `mac=` / `uuid=` 传空即清空该字段（与第 5 条同一实现）；
`KEY ADD` 保留「空值不覆盖已有值」的现有守卫，两者语义不冲突。

**现状**（`:114-118`）：

```python
k["name"] = name
if mac:  k["mac"] = mac
if uuid: k["uuid"] = uuid
```

**为什么必须改**：手环更换、手机重装系统导致 UUID 变化后，旧值**永远清不掉**；
而旧 UUID / 旧名字仍参与匹配（第 11 条），成为无法吊销的残留凭据。

**验收**：`KEY SET 手机-03 uuid=` → 该行 UUID 列为空，名称与地址不变。

### 9. `KEY DEL` 必须支持按 UUID / 序号删除，重名时报错而不是全删

**命中多条时报错并列出候选，禁止一次删多条**。

**现状**（`:131-138`）：

```python
new_keys = [k for k in keys if k.get("name") != name]   # ← 同名全部被过滤掉
```

**验收**：两条同名记录下 `KEY DEL 手机` → 报
`名称重复，请改用 UUID 或序号：1. 手机(UUID=a…) 2. 手机(UUID=b…)`，删除数 = 0；

## 三、匹配与安全（`src/key_matcher.py`）

### 11. 匹配必须「凭据唯一化」：名字彻底退出匹配

**要求**：`_find_key()` 改为**凭据唯一化匹配**——每条记录只用**它自己携带的最强唯一标识**命中，
`name` **任何情况下都不作为匹配凭据**：

```python
def _find_key(self, name, mac, uuid):
    uu = (uuid or "").lower().replace("-", "")
    mc = (mac or "").upper()

    # 1) 记录含 UUID → 只按 UUID 命中
    if uu:
        for k in self._keys:
            if k["uuid"] and uu == k["uuid"]:
                return k

    # 2) 记录含 MAC（且无 UUID）→ 只按 MAC 命中
    if mc:
        for k in self._keys:
            if k["mac"] and not k["uuid"] and mc == k["mac"]:
                return k

    # 3) 记录既无 UUID 也无 MAC → 永不命中（这类记录不应再被创建，见第 7 条）
    return None
```

**现状**（`:134-146`）：三路 OR 并列，任一相等即命中：

```python
if nm and k["name"] and nm == k["name"].lower():  return k
if mc and k["mac"]  and mc == k["mac"]:           return k
if uu and k["uuid"] and uu == k["uuid"]:          return k
```

**为什么必须改（全局优先级最高的一条）**：手机广播带设备名，而 `OPPOReno9` 这类**出厂默认名同型号几千万台完全相同**。
只要白名单里写着这个名字，**任何同款手机靠近都能通电**。
名字是本系统里唯一无法保证唯一性的标识，不能作为凭据使用。

#### ★ 名字为什么必须彻底退出匹配

改造前 `name` 是三路 OR 之一，等于**「设备名就是钥匙」**。对手环这类「没有 UUID、只有名字」的设备，
这条更是唯一凭据——于是出现一个真实漏洞：

> 现役钥匙是**荣耀手环 3，广播名 `honor Band 3-042`**（`docs/05_标定与测试记录.md:5`）。
> 该名字的后缀来自 MAC 尾号，所以同型号手环**有可能**叫出同一个名字（概率约千分之一）；
> 而换成 `Mi Smart Band 4`、`Band 5` 这类**完全不带后缀的出厂名，则同型号全部互通**——
> 邻居戴着同款手环靠近，车直接通电。

**因此第 3 层（只按 `name`）被删除，不留兜底。**
名字在记录里只保留两个职责：**界面展示**、**`KEY SET` / `KEY DEL` 的定位符**。

**手环改按 MAC 匹配，这是可行的**：BLE 手环绝大多数使用 **public static address**
（地址固定，扫描即可拿到，长度形如 `C8:47:8C:1A:2B:3C`），现有登记流程本来就同时记录了 MAC。改用 MAC 后：

- 同型号手环**不再互通**（地址各不相同）；
- 手环换电池 / 重启 / 重新配对后地址不变，钥匙继续有效。

**唯一例外：地址会轮换的设备（RPA 手环）**——这类设备**不能作为钥匙**，
**不得因此回退到名字匹配**（回退等于把漏洞加回来）。因为它没有稳定标识，只能每次使用前重登一次。
**固件不为它做任何特殊处理**（见下条「不新增运行时逻辑」）。

#### ★ 不新增任何运行时逻辑（内存约束）

| 做法 | 内存影响 | 结论 |
|---|---|---|
| 换掉 `_find_key` 的匹配顺序 | **0 字节**（同样的循环、同样的字段） | 采用 |
| 启动时扫描白名单、打印停用告警 | 需额外遍历 + 字符串拼接 | 不做 |
| 记录里增加 `type` / `disabled` / `weak` 等标记字段 | 每条记录 +几~十几字节 × 10 条 | 不做 |
| 兼容旧「仅名字」记录的降级分支 | 多一条判断 + 分支代码 | 不做 |

**旧数据怎么办：请你在升级时手工改一次 `config.json`**，不在固件里做迁移：

```
# 升级前（只有名字，name 不再参与匹配 → 这条已失效）
{"keys": [{"name": "手环-老王", "mac": "", "uuid": ""}]}

# 升级后（SCAN 查到手环地址，手工补进 mac）
{"keys": [{"name": "手环-老王", "mac": "C8:47:8C:1A:2B:3C", "uuid": ""}]}
```

或用第 5 条的 `KEY SET 手环-老王 mac=C8:47:8C:1A:2B:3C` 在串口里改一次，效果相同。
**之后不会再产生这类记录**：第 7 条要求 `KEY ADD` 在 mac 与 uuid 都为空时直接拒绝，从源头上堵住。

> 说明：`main.py` 与 `_load_keys()` 的旧格式兼容路径（`config_mode.py:68-78`、`main.py:34-39`）
> **保持原样不改**——它们只是把旧字段读进来，不增加运行开销；补完 mac 后自然恢复正常。

#### ★ 这不是「同时满足」，而是「只认一个」

**易误读点（必须按下面理解，不要写成 AND 叠加）**：改造后**不是**要求「名字 + MAC 同时相等」
或「名字 + UUID 同时相等」。真实语义是：
**每条记录只启用一个凭据——取它自己携带的最强唯一标识——匹配时只看这一个字段，其余字段完全不参与。**

| 记录里存了什么 | 匹配时只看 | 名字参与吗 | 典型对象 |
|---|---|---|---|
| `name` + `uuid` | **只按 uuid** | 否 | 手机（推荐形态） |
| `name` + `mac` + `uuid` | **只按 uuid** | 否 | 手机（旧数据可能带随机 mac） |
| `name` + `mac`（无 uuid） | **只按 mac** | 否 | 手环（固定地址） |
| 只有 `name`（无 mac 无 uuid） | **不命中任何设备** | — | 升级前的旧数据，手工补 mac 一次 |
| 全空（兜底条目） | 不命中任何设备 | — | 见第 12 条 |

**为什么不能做成 AND**（三条都是实际会发生的）：

1. **手机改名会让钥匙失效**：手机广播名默认就是系统蓝牙名，用户改手机蓝牙名后广播名随之改变
   （App 侧也提供「按编号改名」，如 `OPPOReno9-03`）。若要求「名字 + uuid 同时相等」，
   改个名车就不认了——而 uuid 一直没变。
2. **MAC 对手机是随机的**：Android 广播地址重建广播即变，任何「名字 + MAC」的 AND 判定，
   第二次开机就会永久失效。
3. **名字没有唯一性**：见上一小节——任何「以名字为一等凭据」的方案，都会让同型号设备互相冒充。

**因此**：`name` 只承担**界面展示**与**定位符**两个职责，**在任何情况下都不参与匹配**，没有例外。

**验收**（五条必须全过）：

1. 白名单 `{name: OPPOReno9, uuid: <我的>}` + 另一台同名手机（不同 UUID）靠近 → **不通电**；
2. 白名单 `{name: 手环-老王, mac: <固定地址>, uuid: ""}` + **该手环本人**靠近 → **通电**（能力不退化）；
3. 白名单 `{name: 手环-老王, mac: <固定地址>, uuid: ""}` + 同型号同名但地址不同的手环靠近 →
   **不通电**（本轮核心：同型号不再互通）；
4. 白名单 `{name: 手环-老王, mac: "", uuid: ""}`（旧数据形态）+ 同名手环靠近 →
   **不通电**（名字已不参与匹配）；
5. 白名单 `{name: OPPOReno9-03, uuid: <我的>}`，把手机蓝牙名改成 `新名字` 后靠近（uuid 不变）→
   **仍然通电**（证明不是 AND）。

## 六、每钥匙阈值与多设备（`src/key_matcher.py`）

### 17. 每把钥匙必须有独立通/断电阈值，未设置时回落全局默认

**要求**：阈值从「全局一对」改为「每把钥匙一对，可缺省」。

1. **数据**：`keys` 每条记录可选 `rssi_on` / `rssi_off`；
   **未设置（键不存在或为空）→ 用全局 `cfg["rssi_on"]` / `cfg["rssi_off"]`**。
   现有 `config.json` 不需要改，行为与今天完全一致。
2. **状态必须按钥匙分开累计**：`streak` / `far_streak` 不能共用计数器，
   因为每把钥匙的阈值不同，混算会互相污染（A 的强帧替 B 攒 streak）。
3. **命令**：`KEY SET <名> rssi_on=-65 rssi_off=-80` 可设；`rssi_on=` 传空 → 清除，回落默认。
4. **`KEY LIST` 显示来源**：`阈值=-65/-80(自定义)` 或 `阈值=默认(-80/-90)`，
   让人一眼看出这行用的是哪套值。

**现状**（三处都是全局单值，与帧来自哪把钥匙无关）：

- `config.py:29-30`：`"rssi_on": -60, "rssi_off": -75`（现网 `config.json` 为 -80/-90）
- `main.py:95-103`：构造 `KeyMatcher` 只传 `cfg["rssi_on"]` / `cfg["rssi_off"]`
- `key_matcher.py:65,70`：`update()` 用 `self._rssi_on` 比较**每一帧**

**为什么必须改**：不同设备的发射功率与佩戴衰减差到 10~15 dB：

| 设备 | 典型发射 | 佩戴场景 | 合适阈值（示例，需现场标定） |
|---|---|---|---|
| 手环 | 0 dBm | 贴腕、无遮挡 | `-65 / -78` |
| 手机 | +1 dBm | 裤兜、人体吸收 | `-80 / -90` |
| 手机 | +1 dBm | 背包 / 金属遮挡 | `-82 / -92` |

统一一对值的必然结果：**要么手环贴着车才通电**（阈值偏严），**要么手机在客厅就通电**（阈值偏松）。

> 补一个实测前提：RSSI 数值范围是 -127~+20，但 BLE 1M 的实际接收灵敏度约 -95~-100 dBm。
> 弱于这个量级是**丢包**（根本没有该帧），不是「测到 -100」。所以断电判断只能靠
> 「一段时间收不到帧」（`loss_timeout_s`），不能靠低阈值。标定区间建议限制在 -60 ~ -95。

**实现要点（省内存）**：

```python
# 不要用 `k.get("rssi_on") or self._rssi_on`：0 会被误判为"未设置"
on  = k["rssi_on"]  if k.get("rssi_on")  not in (None, "") else self._rssi_on
off = k["rssi_off"] if k.get("rssi_off") not in (None, "") else self._rssi_off
```

阈值不缓存到新对象，按帧从记录里取（一次 dict 取值，无分配）。

**验收**：

1. 手环设 `-65/-78`、手机设 `-80/-90`：手环 1 m 处通电，手机 3 m 处**不**通电
   （数值按现场标定，只验「两把互不影响」）；
2. 未设阈值的钥匙，行为与改造前**逐帧一致**；
3. `KEY LIST` 能区分「自定义 / 默认」；
4. `KEY SET 名 rssi_on=` 清除后，该钥匙回到默认值。

### 18. 多把钥匙：聚合判定 + 显示「触发通电的那把」

**要求**：两件事一起改，它们共用第 17 条那份每钥匙状态。

#### 1）聚合判定（否则"谁先走谁断电"）

| 规则 | 说明 |
|---|---|
| **任一**钥匙达到 NEAR 条件 → 整体 NEAR（通电） | 两把都在车边时不会互相干扰 |
| **所有**钥匙都判 FAR 或已失联（超 `loss_timeout_s`）→ 才整体 FAR（断电） | 一把走远、另一把贴车 → **不断电** |

现状是单一全局状态：一把钥匙走远、弱帧累计够 `far_frames` 就整体判 FAR，**哪怕另一把就在车边**。

#### 2）显示「触发通电的那把」

- `钥匙=` 显示**当前把电通上的那把** = 最近一次满足 NEAR 条件（`streak >= hit_frames`）的钥匙；
- 该钥匙不再满足时，由**仍在满足**的另一把接管（不显示失效的那把）；
- 整体 FAR 时显示 `-`；
- 同时带信号：`钥匙=手环-老王(-62)`，RSSI 取**该钥匙最近一帧**的值（不是最后到达的那帧）。

**现状**（`main.py:289` 输出 `钥匙=%s`）：

- `last_key_name` = **最后一次匹配帧**的钥匙（`key_matcher.py:64`）；
- `best_rssi` = **最后一帧**的 RSSI，不是该钥匙自己的最新值。

**为什么必须改**：手机 iBeacon 250 ms/帧 ≈ 4 帧/秒，手环约 2~3 帧/秒——
按「最后一帧」显示，界面**几乎永远显示手机**，哪怕手环正贴在手腕上。

**实现要点（不新增缓存）**：

- 每把钥匙状态记 `streak` / `far_streak` / `last_seen` / `last_rssi`（4 个整数，≈16 B/把）；
- `active_key` 只存**对现有记录 dict 的引用**（不 copy、不 concat 字符串）；
- 显示时取 `active_key["name"]` 与 `active_key_state.last_rssi`，格式化一次输出。

**验收**：

1. 手环 + 手机同时在旁 → 通电；`钥匙=` 显示**先进入 NEAR 的那把**；
2. 把该把拿远（另一把仍在车边）→ **仍通电**，显示自动切到另一把；
3. 两把都拿远 → 断电，显示 `-`；
4. 显示格式含 RSSI，且名字与 `KEY LIST` 完全一致；
5. 单钥匙场景（只有一把）行为与改造前一致。

## 七、名称与参数解析（工具 + 固件）

### 19. 名称与参数解析必须对空白零容忍

**要求**（三处，缺一不可）：

#### ① 固件做参数个数校验

不符预期立刻报错 + 打印用法，**禁止「尽量猜」**：

| 命令 | 合法个数 | 说明 |
|---|---|---|
| `KEY ADD` | `len(parts)` = **4 或 5** | 4 = `<名称> <MAC>`；5 = `<名称> <MAC> <UUID>` |
| `KEY SET` | `len(parts)` ≥ **3**，且第 3 项起全为 `k=v` | `<定位符> key=value ...` |
| `KEY DEL` | `len(parts)` = **3** | `<名称或UUID或序号>` |

报错文案：

```
参数个数不对（收到 5 个字段）。用法：KEY ADD <名称> <MAC> [UUID]，名称不能含空格
```

#### ② 固件校验名称不得含空白

（`" "` / `\t` / 全角空格）

```
名称不能包含空格。请用 - 连接，如：手机-03
```

#### ③ Qt 工具命名框

默认值必须把空白替换成 `-`；**提交前再校验一次**，仍含空白则就地报错、**不发送命令**。

---

**现状**（三处缺口叠加，形成一条「静默失败路径」）：

| 位置 | 代码 | 问题 |
|---|---|---|
| `serial_monitor_qt.py:721` | `cmd = "KEY ADD %s %s %s" % (name, mac, uuid)` | 名字原样拼进命令，无转义、无引号 |
| `serial_monitor_qt.py:703` | `name = (...).strip()` | 只去**首尾**空白，中间空格原样保留 |
| `config_mode.py:295-310` | `parts = cmd.split()` 后直接取 `parts[2]/[3]/[4]` | **无参数个数校验**，少/多都照取不误 |

**为什么必须改（这是当前最高频的踩坑路径，比第 6、7 条更容易撞）**：

手机广播的设备名**就是系统蓝牙名**——Android 没有「把自定义字符串写进广播」的 API。
而典型出厂名带空格：

```
OPPO Reno9      HUAWEI Mate 40      Redmi Note 12      Xiaomi 13 Pro
```

于是工具发出去的是：

```
KEY ADD OPPO Reno9 AA:BB:CC:DD:EE:FF 6272...0003
        └──┬───┘ └──┬──┘ └─────┬──────┘
        parts[2]  parts[3]   parts[4]
          名称   ← 当成 MAC   ← 当成 UUID
```

登记结果：**名称只剩 `OPPO`，MAC 变成 `Reno9`，UUID 变成真实 MAC** —— 一条永远匹配不上的死记录。
而工具只打印「已发送添加钥匙命令」，**没有任何报错**。用户以为成功，到车边却不通电。

> 注意：这**不是**「手打才有的问题」。工具只省掉了手打 32 位 UUID，
> 名字这条路径它同样会错——而绝大多数手机出厂名都带空格。

**验收**（四条全过）：

1. 手发 `KEY ADD OPPO Reno9 AA:BB:CC:DD:EE:FF <32位uuid>` → **拒绝**并提示「名称不能包含空格」，
   `KEY LIST` 不变；
2. 手发 `KEY ADD 手机-03`（缺 MAC）→ 报「参数个数不对」+ 用法，`KEY LIST` 不变；
3. 工具内选一个名为 `OPPO Reno9` 的设备 → 命名框**预填 `OPPO-Reno9`**（空格已替换）→
   确认后 `KEY LIST` 名称正确、UUID = 扫描值；
4. 在命名框手动输入 `我的 手机`（带空格）→ **不发送任何命令**，就地报错。

**内存代价：0 常驻。** 个数校验是对已有 `parts` 做一次 `len()`；名称校验是一次 `" " in name` 判断。
都在原有解析路径内，不新增字段、不新增缓存、不新增字符串常量表。

## 十、术语与命令速查

### 10.1 术语

| 术语 | 含义 |
|---|---|
| **定位符** | `KEY SET` / `KEY DEL` 里用来指定「哪一条记录」的字符串。解析顺序：名称 → UUID（归一化后）→ `KEY LIST` 的 1-based 序号 |
| **归一化（UUID）** | 去连字符、去首尾空白、转小写，得到 32 字符小写 hex |
| **归一化（占位）** | `-` / `_` / `none` / `null` → 空字符串 |
| **NEAR / FAR** | 匹配器的两个状态：近（达到通电条件）/ 远（达到断电条件） |
| **`streak`** | 连续满足「达到本把钥匙 `rssi_on`」的帧数 |
| **`far_streak`** | 连续满足「低于本把钥匙 `rssi_off`」的帧数 |
| **`loss_timeout_s`** | 超过这个时长收不到帧即判失联（现为 15 秒），`best_rssi` 返回 None |
| **`power_off_delay_s`** | 判 FAR 后延时多久断电（现为 60 秒） |

### 10.2 改完后的命令集

```
KEY LIST                                            # 首行含「共 N 把，上限 10」
KEY ADD  <名称> <MAC> [UUID]                        # 只新增；重名/重复一律拒绝
KEY SET  <名称|UUID|序号> [name=..] [mac=..] [uuid=..] [rssi_on=..] [rssi_off=..]
                                                    # 只改显式出现的字段；传空 = 清空
KEY DEL  <名称|UUID|序号>                            # 命中多条即报错，禁止批量删
EXIT                                                # 退出配置模式
```

三条通用规则：

1. **名称不能含空白**，需要分隔请用 `-`（`手机-03`）；
2. **跳过某个字段用 `-`**（会被归一化为空），且**不要用连续两个空格**跳过；
3. **UUID 用 32 位小写无连字符**；带连字符也能收（第 13 条归一化），但输出统一为无连字符。

### 11.2 实现口径说明（与要求单的细微差异，均已对齐意图）

1. **`KEY SET name=`（空值）拒绝**：要求单未规定；因名称是首选定位符，清空会让该记录无法用名称定位，
   故报「名称不能为空（如需删除请用 KEY DEL）」。
2. **SCAN 去重在 UUID 优先之外保留同轮 MAC 合并**：iBeacon 广播与 SCAN_RSP 设备名分属两包、
   MAC 在单轮扫描内稳定，必须合并才能把名字挂到 UUID 设备上；跨轮每次重建列表，
   "手机重建广播后地址变了"的问题已由 UUID 优先解决。
3. **工具 ✔ 标记依赖最近一次 KEY LIST 数据**（要求单 4.1 已认可此约束）；改名/删除后弹窗自动刷新，
   刷新后重新 SCAN 标记即正确。
4. **`KEY SET` 仅定位符不带字段**（合法个数下限）：视为无操作，按约定打印更新后的完整三元组。
5. **旧格式迁移**：`config.json` 旧字段 `key_names/key_macs` 仍可读（按位合并为只有名字+MAC 的记录）；
   其中"只有名字"的记录按第 11 条永不命中，KEY LIST 会原样显示，需按 §三.4 手工补 MAC 或登记 UUID。
