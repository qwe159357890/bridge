## 零、背景与范围

Bridge 客户端（`my.bridge.com`）以手机身份作为 BLE peripheral 持续广播一条 **iBeacon**，
espAutoUnlock 扫到后按 UUID 认定为钥匙。**该链路已实测跑通**：

- 手机主包为 iBeacon（company `0x004C`、`0215`、16 字节 UUID），设备名放在 scan response；
- `parse_ibeacon_uuid()`（`src/ble_scanner.py:71-95`）正确解出 32 字符小写无连字符 UUID；
- `KEY ADD` 登记后 `SCAN` 可见、`KEY LIST` 可见；近远判定、迟滞、`loss_timeout_s` 全部按原设计工作。

**本单只涉及「钥匙登记之后怎么管」**，共 19 条，全部要求修改：

| 组 | 范围 | 条目 |
|---|---|---|
| 一 | 工具界面（`tools/serial_monitor_qt.py`） | 1 ~ 4 |

| 三 | 匹配与安全（`src/key_matcher.py`） | 11 ~ 13 |

### 1. 钥匙列表必须可编辑：加「改名」「删除」两个按钮

### 2. 添加钥匙时必须一律弹出命名框

**要求**：`➕ 添加选中为钥匙` **无论设备是否有名字，一律弹出命名对话框**，预填值按优先级取：`扫描到的设备名` → `"手机-" + UUID前6位` → `"钥匙"`。用户取消或留空则不添加。

**现状**（`serial_monitor_qt.py:703-717`）：只有设备名称为空时才弹窗，有名字就直接沿用：
```python
if uuid and not name:                      # ← 只有"无名字"才弹窗
    default_name = "手机-" + uuid[:6]
    text, ok = QInputDialog.getText(...)
```

**为什么必须改**：名字在这套系统里不是可有可无的标签——它是 `KEY SET` / `KEY DEL` 的**首选定位符**（第 5、9 条），也是界面展示名。而名字在登记瞬间被写死、之后只能靠工具改（第 1 条），登记时不给确认机会，就会留下一串改不掉的名字。

**实现要点**：预填后用户按回车即可确认，手环场景只多一次回车，不改变原有习惯。

**验收**：选中带名字的设备点添加 → 必然弹出预填框；改成 `手机-03` 后 `KEY LIST` 显示 `手机-03`；取消对话框 → 不新增任何记录。

## 二、固件数据正确性（`src/config_mode.py`）

### 5. 必须新增 `KEY SET` 命令（支持改名 / 改字段 / 清空字段）

**要求**：新增命令，其余命令保持不变：

```
KEY SET <定位符> [name=<新名>] [mac=<新mac>] [uuid=<新uuid>]
```

**语义（逐条不可改）**：

| 项 | 规定 |
|---|---|
| 定位符解析顺序 | ① 名称精确匹配 → ② UUID（归一化后）匹配 → ③ `KEY LIST` 的 1-based 序号 |
| 只更新什么 | 仅更新命令中**显式出现**的字段，未出现的字段不动 |
| 显式空值 | `mac=` / `uuid=` 传空 → **清空该字段**（解决第 8 条） |
| 命中多条 | **报错并列出全部候选**（`名称重复，请改用 UUID 或序号：1. … 2. …`），不猜 |
| 未命中 | 报错 `未找到钥匙: <定位符>`，**不新增**（`SET` 绝不退化为 `ADD`） |
| 成功输出 | 打印改后的完整三元组 `名称=… 地址=… UUID=…` |

**现状**：命令集只有 `KEY LIST` / `KEY ADD` / `KEY DEL`（`config_mode.py:295-310`，帮助文本 `:5`/`:326`/`:335`）。

**为什么必须改**：没有 `SET`，任何编辑都退化为「先 `DEL` 再 `ADD`」。中间态里这把钥匙**不存在**——若此时人已在车上、车已通电，`_find_key` 找不到钥匙 → 15 秒判 FAR → 60 秒后断电。**改一次钥匙 = 一次潜在断电。**

**实现要点**：
- 在 `_handle_cmd()` 内新增 `sub == "SET"` 分支；`cmd.split()`（`:288`）后再拆 `k=v`，`name` 值不允许含空格；
- 复用 `_load_keys()` / `_save_keys()`，写盘后保持旧字段 `key_names`/`key_macs` 同步（`:90-91` 现有逻辑不动）。

**验收**：
- `KEY SET 手机-03 name=手机-A` → `KEY LIST` 显示 `手机-A`，UUID 不变；
- `KEY SET 手机-03 mac=` → 该行地址列为空，UUID 不变；
- `KEY SET 不存在的名字 name=x` → 只报错，钥匙总数不变。

### 6. `KEY ADD` 改为「只新增」，重名/重复必须拒绝而不是覆盖

**要求**：`KEY ADD` 命中已有记录时**一律拒绝并报错**，禁止静默覆盖；更新统一走 `KEY SET`（第 5 条）。

**拒绝口径（三种，文案必须区分）**：

| 冲突 | 报错文案 |
|---|---|
| 名称已存在 | `名称已存在：手机。请换一个名字，或使用 KEY SET 改名。` |
| UUID 已登记 | `该 UUID 已登记为「手机-03」，无需重复添加。` |
| MAC 已登记 | `该地址已登记为「手环-老王」，无需重复添加。` |

**现状**（`:110-122`）：
```python
for k in keys:
    if (k.get("name") == name or (mac and k.get("mac") == mac)
            or (uuid and k.get("uuid") == uuid)):
        k["name"] = name            # ← 名字被后加的覆盖
        ...
        _log.info("钥匙已更新: ...")  # ← 只报"更新"，用户以为加了新的
```

**为什么必须改**：两台手机都叫 `手机` 时，第二台直接把第一台覆盖，日志写「钥匙已更新」，`KEY LIST` 仍然 1 把。用户以为登记了两台，实际只有一台能通电——**静默数据丢失**，且表现为「偶发不解锁」，几乎无法排查。

**验收**：连续添加两台同名手机 → 第二次明确报「名称已存在」；`KEY LIST` 仍是 1 把且**未被修改**；改成不同名字后添加成功，变 2 把。

**名字唯一是硬约束，不接受例外**（请照此实现，不要加「同名但 UUID 不同就放行」的分支）：

- 判定只比较**名称字符串**，**与 mac / uuid 是否相同无关**。第一台叫 `手机一`，第二台也叫 `手机一` 但 mac、uuid 全都不同 → **照样拒绝**；
- 同一台设备重复添加（UUID 相同、名称也相同）→ 同样拒绝，提示「该 UUID 已登记为…」；要改就 `KEY SET`；
- 同一个人有两台设备（手机 + 手环）→ 必须区分命名：`手机一-手机`、`手机一-手环`。这是本约束的既定代价，**不允许为了让它们同名而放宽**。

**为什么名字必须唯一**：名称同时是 `KEY SET`（第 5 条）和 `KEY DEL`（第 9 条）的**首选定位符**。一旦允许同名，这两条命令的「按名字找」就会指向多行，只能退化成「报错让用户改用 UUID」，那等于把定位符能力废掉，且历史上已经产生重名数据（见第 9 条候选列表）。**宁可要求用户多打四个字，也不让命令产生歧义。**

### 7. `-` 占位必须归一化为空，且空字段不参与去重

**要求**：`KEY ADD` / `KEY SET` 解析时，把 `-`、`_`、`none`、`null`（不区分大小写）统一归一化为**空字符串**：

```python
def _norm(v):
    return "" if (v or "").strip().lower() in ("-", "_", "none", "null") else (v or "").strip()
mac, uuid = _norm(mac), _norm(uuid)
```

并且：**空字段一律不参与去重比较**（第 6 条的三种冲突判定里，空值跳过）。

**新增硬校验（防止产生永远匹配不上的死记录）**：
- `name`、`mac`、`uuid` **三者全空** → 拒绝：`名称、地址、UUID 不能全为空`；
- **`mac` 与 `uuid` 同时为空**（只给了名字）→ 拒绝：`仅有名称无法作为钥匙。请提供地址或 UUID：KEY ADD <名称> <MAC>`。

**现状**：`-` 被原样存成 `mac="-"`（`:302` `mac = parts[3]`，无校验）。于是第二台手机同样传 `-` 时，去重条件 `mac 相同` 命中（`"-" == "-"`）→ **第二台覆盖第一台**。

**为什么必须改**：手机钥匙的正确用法就是「没有固定 MAC」（Android 随机地址），所以**每台手机都会走 `-`**——这是必踩路径，不是边缘情况。而只给名字的记录在第 11 条之后永远匹配不上，属于必被拒绝的无效配置。

**验收**：
- `KEY ADD 手机-03 - <uuidA>`、`KEY ADD 手机-04 - <uuidB>` → `KEY LIST` **两把**，地址列均为空，互不覆盖；
- `KEY ADD 空钥匙 - -` → 拒绝并报错；
- `KEY ADD 只有名字 - -` → 拒绝并提示「仅有名称无法作为钥匙」。

### 9. `KEY DEL` 必须支持按 UUID / 序号删除，重名时报错而不是全删

**为什么必须改**：`KEY DEL 手机` 会把所有叫 `手机` 的记录一次删光且**不可撤销**；同时按序号删除是第 1 条「列表内删除」的必要前提。

**验收**：两条同名记录下 `KEY DEL 手机` → 报 `名称重复，请改用 UUID 或序号：1. 手机(UUID=a…) 2. 手机(UUID=b…)`，删除数 = 0；`KEY DEL 2` → 精确删第 2 条。

## 三、匹配与安全（`src/key_matcher.py`）

### 11. 匹配必须「凭据唯一化」：名字彻底退出匹配

**要求**：`_find_key()` 改为**凭据唯一化匹配**——每条记录只用**它自己携带的最强唯一标识**命中，`name` **任何情况下都不作为匹配凭据**：

```python
def _find_key(self, name, mac, uuid):
    uu = (uuid or "").lower().replace("-", "")
    mc = (mac or "").upper()

    # 1) 记录含 UUID → 只按 UUID 命中
    if uu:
        for k in self._keys:
            if k["uuid"] and uu == k["uuid"]:
                return k

    # 2) 记录含 MAC（且无 UUID）→ 只按 MAC 命中
    if mc:
        for k in self._keys:
            if k["mac"] and not k["uuid"] and mc == k["mac"]:
                return k

    # 3) 记录既无 UUID 也无 MAC → 永不命中（这类记录不应再被创建，见第 7 条）
    return None
```

**现状**（`:134-146`）：三路 OR 并列，任一相等即命中：
```python
if nm and k["name"] and nm == k["name"].lower():  return k
if mc and k["mac"]  and mc == k["mac"]:           return k
if uu and k["uuid"] and uu == k["uuid"]:          return k
```

**为什么必须改（本单最高优先级）**：手机广播带设备名，而 `OPPOReno9` 这类**出厂默认名同型号几千万台完全相同**。只要白名单里写着这个名字，**任何同款手机靠近都能通电**。名字是本系统里唯一无法保证唯一性的标识，不能作为凭据使用。

### ★ 名字为什么必须彻底退出匹配（本轮新增决定）

改造前 `name` 是三路 OR 之一，等于**「设备名就是钥匙」**。对手环这类「没有 UUID、只有名字」的设备，这条更是唯一凭据——于是出现一个真实漏洞：

> 你的现役钥匙是**荣耀手环 3，广播名 `honor Band 3-042`**（`docs/05_标定与测试记录.md:5`）。
> 该名字的后缀来自 MAC 尾号，所以同型号手环**有可能**叫出同一个名字（概率约千分之一）；
> 而换成 `Mi Smart Band 4`、`Band 5` 这类**完全不带后缀的出厂名，则同型号全部互通**——
> 邻居戴着同款手环靠近，车直接通电。

**因此第 3 层（只按 `name`）被删除，不留兜底**。名字在记录里只保留两个职责：**界面展示**、**`KEY SET` / `KEY DEL` 的定位符**。

**手环改按 MAC 匹配，这是可行的**：BLE 手环绝大多数使用 **public static address**（地址固定，扫描即可拿到，长度形如 `C8:47:8C:1A:2B:3C`），现有登记流程本来就同时记录了 MAC。改用 MAC 后：
- 同型号手环**不再互通**（地址各不相同）；
- 手环换电池/重启/重新配对后地址不变，钥匙继续有效。

**唯一例外：地址会轮换的设备（RPA 手环）**——这类设备**不能作为钥匙**，**不得因此回退到名字匹配**（回退等于把漏洞加回来）。因为它没有稳定标识，只能每次使用前重登一次。**固件不为它做任何特殊处理**（见下条「不新增运行时逻辑」）。

### ★ 不新增任何运行时逻辑（内存约束）

**这是开发板，RAM 极小，第 11 条的实现必须是「纯替换」而不是「加功能」**：

| 做法 | 内存影响 | 结论 |
|---|---|---|
| 换掉 `_find_key` 的匹配顺序 | **0 字节**（同样的循环、同样的字段） | ✅ 采用 |
| 启动时扫描白名单、打印停用告警 | 需额外遍历 + 字符串拼接 | ❌ 不做 |
| 记录里增加 `type` / `disabled` / `weak` 等标记字段 | 每条记录 +几~十几字节 × 10 条 | ❌ 不做 |
| 兼容旧「仅名字」记录的降级分支 | 多一条判断 + 分支代码 | ❌ 不做 |

**旧数据怎么办：由你（作者）在升级时手工改一次 `config.json`**，不在固件里做迁移：

```
# 升级前（只有名字，name 不再参与匹配 → 这条已失效）
{"keys": [{"name": "手环-老王", "mac": "", "uuid": ""}]}

# 升级后（SCAN 查到手环地址，手工补进 mac）
{"keys": [{"name": "手环-老王", "mac": "C8:47:8C:1A:2B:3C", "uuid": ""}]}
```

或用第 5 条的 `KEY SET 手环-老王 mac=C8:47:8C:1A:2B:3C` 在串口里改一次，效果相同。
**之后不会再产生这类记录**：第 7 条要求 `KEY ADD` 在 mac 与 uuid 都为空时直接拒绝，从源头上堵住。

> 说明：`main.py` 与 `_load_keys()` 的旧格式兼容路径（`config_mode.py:68-78`、`main.py:34-39`）**保持原样不改**——它们只是把旧字段读进来，不增加运行开销；补完 mac 后自然恢复正常。

### ★ 这不是「同时满足」，而是「只认一个」

**易误读点（必须按下面理解，不要写成 AND 叠加）**：改造后**不是**要求「名字 + MAC 同时相等」或「名字 + UUID 同时相等」。
真实语义是：**每条记录只启用一个凭据——取它自己携带的最强唯一标识——匹配时只看这一个字段，其余字段完全不参与。**

| 记录里存了什么 | 匹配时只看 | 名字参与吗 | 典型对象 |
|---|---|---|---|
| `name` + `uuid` | **只按 uuid** | 否 | 手机（推荐形态） |
| `name` + `mac` + `uuid` | **只按 uuid** | 否 | 手机（旧数据可能带随机 mac） |
| `name` + `mac`（无 uuid） | **只按 mac** | 否 | 手环（固定地址） |
| 只有 `name`（无 mac 无 uuid） | **不命中任何设备** | — | 升级前的旧数据，手工补 mac 一次 |
| 全空（兜底条目） | 不命中任何设备 | — | 见第 12 条 |

**为什么不能做成 AND**（三条都是实际会发生的）：

1. **手机改名会让钥匙失效**：本系统的广播名默认是「系统名 + 编号」（如 `OPPOReno9-03`），用户改手机蓝牙名后广播名就变。若要求「名字 + uuid 同时相等」，改个名车就不认了——而 uuid 一直没变。
2. **MAC 对手机是随机的**：Android 广播地址重建广播即变，任何「名字 + MAC」的 AND 判定，第二次开机就会永久失效。
3. **名字没有唯一性**：见上一小节——任何「以名字为一等凭据」的方案，都会让同型号设备互相冒充。

**因此**：`name` 在记录里只承担两个职责——**界面展示**与**`KEY SET` / `KEY DEL` 的定位符**；它**在任何情况下都不参与匹配**，没有例外。

**验收**（五条必须全过）：
1. 白名单 `{name: OPPOReno9, uuid: <我的>}` + 另一台同名手机（不同 UUID）靠近 → **不通电**；
2. 白名单 `{name: 手环-老王, mac: <固定地址>, uuid: ""}` + **该手环本人**靠近 → **通电**（手环能力不退化）；
3. 白名单 `{name: 手环-老王, mac: <固定地址>, uuid: ""}` + 同型号同名但地址不同的手环靠近 → **不通电**（本轮核心：同型号不再互通）；
4. 白名单 `{name: 手环-老王, mac: "", uuid: ""}`（旧数据形态）+ 同名手环靠近 → **不通电**（名字已不参与匹配）；
5. 白名单 `{name: OPPOReno9-03, uuid: <我的>}`，把手机蓝牙名改成 `新名字` 后靠近（uuid 不变）→ **仍然通电**（证明不是 AND）。

### 13. UUID 必须归一化后再存储与比较

**要求**：新增统一函数，在 `KEY ADD`、`KEY SET`、`_normalize()` **三处**调用：

def _norm_uuid(s):
    return (s or "").replace("-", "").strip().lower()

## 四、扫描与展示

### 14. `SCAN` 去重键必须改为 UUID 优先

**要求**：
- 去重键：**UUID 优先**；无 UUID 时用 `(name, mac)`；都无则用 `mac`；
- 设备列表对**带 UUID 的设备**，地址列显示 `(随机)`（灰显），不再展示无意义的随机地址；
- 排序：带 UUID 且有名字的设备置顶。

**现状**（`config_mode.py:265-278`）：按 `mac` 建字典去重，后到的非空名字覆盖先到的空名。

**为什么必须改**：手机 BLE 地址是随机静态地址，重建广播即变化。按 MAC 去重的结果是同一条记录在跨轮扫描中「地址变了就成了另一行」，而用户恰恰只能靠地址列辨认设备。手环没有 UUID，改为 UUID 优先后其行为不变。

**验收**：手机重建广播后再 `SCAN` → 列表里始终只有一行；手环（无 UUID）仍正常显示真实地址。

### 15. 必须提供 UUID 短码，避免人工比对 32 位串

**要求**：钥匙列表与设备列表统一增加「短码」列，取 UUID **前 8 位**（如 `62726964`）；完整值保留在原 UUID 列或悬浮提示中。

**现状**：两个列表各自展示完整 32 位串，用户核对「这台设备对应哪把钥匙」只能逐字符比对。

**为什么必须改**：这是第 6/7 条覆盖问题长期不被发现的原因——多把钥匙/多台设备同屏时，肉眼无法可靠区分。

**验收**：两台同型号手机同屏时，靠短码可一眼区分；短码与 UUID 前 8 位一致。

## 六、每钥匙阈值与多设备（`src/key_matcher.py`）

### 17. 每把钥匙必须有独立通/断电阈值，未设置时回落全局默认

**要求**：阈值从「全局一对」改为「每把钥匙一对，可缺省」。

1. **数据**：`keys` 每条记录可选 `rssi_on` / `rssi_off`；**未设置（键不存在或为空）→ 用全局 `cfg["rssi_on"]` / `cfg["rssi_off"]`**。现有 `config.json` 不需要改，行为与今天完全一致。
2. **状态必须按钥匙分开累计**：`streak` / `far_streak` 不能共用计数器，因为每把钥匙的阈值不同，混算会互相污染（A 的强帧替 B 攒streak）。
3. **命令**：`KEY SET <名> rssi_on=-65 rssi_off=-80` 可设；`rssi_on=` 传空 → 清除，回落默认。
4. **`KEY LIST` 显示来源**：`阈值=-65/-80(自定义)` 或 `阈值=默认(-80/-90)`，让人一眼看出这行用的是哪套值。

**现状**（三处都是全局单值，与帧来自哪把钥匙无关）：
- `config.py:29-30`：`"rssi_on": -60, "rssi_off": -75`（现网 `config.json` 为 -80/-90）
- `main.py:95-103`：构造 `KeyMatcher` 只传 `cfg["rssi_on"]` / `cfg["rssi_off"]`
- `key_matcher.py:65,70`：`update()` 用 `self._rssi_on` 比较**每一帧**

**为什么必须改**：不同设备的发射功率与佩戴衰减差到 10~15 dB：

| 设备 | 典型发射 | 佩戴场景 | 合适阈值（示例） |
|---|---|---|---|
| 手环 | 0 dBm | 贴腕、无遮挡 | `-65 / -78` |
| 手机 | +1 dBm | 裤兜、人体吸收 | `-80 / -90` |
| 手机 | +1 dBm | 背包/金属遮挡 | `-82 / -92` |

统一一对值的必然结果：**要么手环贴着车才通电**（阈值偏严），**要么手机在客厅就通电**（阈值偏松）。

**实现要点（省内存）**：
```python
# 不要用 `k.get("rssi_on") or self._rssi_on`：0 会被误判为"未设置"
on  = k["rssi_on"]  if k.get("rssi_on")  not in (None, "") else self._rssi_on
off = k["rssi_off"] if k.get("rssi_off") not in (None, "") else self._rssi_off
```
阈值不缓存到新对象，按帧从记录里取（一次 dict 取值，无分配）。

**验收**：
1. 手环设 `-65/-78`、手机设 `-80/-90`：手环 1 m 处通电，手机 3 m 处**不**通电（数值按现场标定，只验"两把互不影响"）；
2. 未设阈值的钥匙，行为与改造前**逐帧一致**；
3. `KEY LIST` 能区分「自定义 / 默认」；
4. `KEY SET 名 rssi_on=` 清除后，该钥匙回到默认值。

### 18. 多把钥匙：聚合判定 + 显示「触发通电的那把」

**要求**：两件事一起改，它们共用第 17 条那份每钥匙状态。

**1）聚合判定（否则"谁先走谁断电"）**

| 规则 | 说明 |
|---|---|
| **任一**钥匙达到 NEAR 条件 → 整体 NEAR（通电） | 两把都在车边时不会互相干扰 |
| **所有**钥匙都判 FAR 或已失联（超 `loss_timeout_s`）→ 才整体 FAR（断电） | 一把走远、另一把贴车 → **不断电** |

现状是单一全局状态：一把钥匙走远、弱帧累计够 `far_frames` 就整体判 FAR，**哪怕另一把就在车边**。

**2）显示「触发通电的那把」**

- `钥匙=` 显示**当前把电通上的那把** = 最近一次满足 NEAR 条件（`streak >= hit_frames`）的钥匙；
- 该钥匙不再满足时，由**仍在满足**的另一把接管（不显示失效的那把）；
- 整体 FAR 时显示 `-`；
- 同时带信号：`钥匙=手环-老王(-62)`，RSSI 取**该钥匙最近一帧**的值（不是最后到达的那帧）。

**现状**（`main.py:289` 输出 `钥匙=%s`）：
- `last_key_name` = **最后一次匹配帧**的钥匙（`key_matcher.py:64`）；
- `best_rssi` = **最后一帧**的 RSSI，不是该钥匙自己的最新值。

**为什么必须改**：手机 iBeacon 250 ms/帧 ≈ 4 帧/秒，手环约 2~3 帧/秒——
按「最后一帧」显示，界面**几乎永远显示手机**，哪怕手环正贴在手腕上。

**实现要点（不新增缓存）**：
- 每把钥匙状态记 `streak` / `far_streak` / `last_seen` / `last_rssi`（4 个整数，≈16 B/把）；
- `active_key` 只存**对现有记录 dict 的引用**（不 copy、不 concat 字符串）；
- 显示时取 `active_key["name"]` 与 `active_key_state.last_rssi`，格式化一次输出。

**验收**：
1. 手环 + 手机同时在旁 → 通电；`钥匙=` 显示**先进入 NEAR 的那把**；
2. 把该把拿远（另一把仍在车边）→ **仍通电**，显示自动切到另一把；
3. 两把都拿远 → 断电，显示 `-`；
4. 显示格式含 RSSI，且名字与 `KEY LIST` 完全一致；
5. 单钥匙场景（只有一把）行为与改造前一致。

## 七、名称与参数解析（工具 + 固件）

### 19. 名称与参数解析必须对空白零容忍

**要求**（三处，缺一不可）：

**① 固件做参数个数校验**，不符预期立刻报错 + 打印用法，**禁止「尽量猜」**：

| 命令 | 合法个数 | 说明 |
|---|---|---|
| `KEY ADD` | `len(parts)` = **4 或 5** | 4 = `<名称> <MAC>`；5 = `<名称> <MAC> <UUID>` |
| `KEY SET` | `len(parts)` ≥ **3**，且第 3 项起全为 `k=v` | `<定位符> key=value ...` |
| `KEY DEL` | `len(parts)` = **3** | `<名称或UUID或序号>` |

报错文案：
```
参数个数不对（收到 5 个字段）。用法：KEY ADD <名称> <MAC> [UUID]，名称不能含空格
```

**② 固件校验名称不得含空白**（`" "` / `\t` / 全角空格）：
```
名称不能包含空格。请用 - 连接，如：手机-03
```

**③ Qt 工具命名框**：默认值必须把空白替换成 `-`；**提交前再校验一次**，仍含空白则就地报错、**不发送命令**。

---

**现状**（三处缺口叠加，形成一条「静默失败路径」）：

| 位置 | 代码 | 问题 |
|---|---|---|
| `serial_monitor_qt.py:721` | `cmd = "KEY ADD %s %s %s" % (name, mac, uuid)` | 名字原样拼进命令，无转义、无引号 |
| `serial_monitor_qt.py:703` | `name = (...).strip()` | 只去**首尾**空白，中间空格原样保留 |
| `config_mode.py:295-310` | `parts = cmd.split()` 后直接取 `parts[2]/[3]/[4]` | **无参数个数校验**，少/多都照取不误 |

**为什么必须改（这是当前最高频的踩坑路径，比第 6、7 条更容易撞）**：

手机广播的设备名**就是系统蓝牙名**——Android 没有「把自定义字符串写进广播」的 API
（`AdvertiseData.Builder` 只有 `setIncludeDeviceName(boolean)`）。而典型出厂名带空格：

```
OPPO Reno9      HUAWEI Mate 40      Redmi Note 12      Xiaomi 13 Pro
```

于是工具发出去的是：

```
KEY ADD OPPO Reno9 AA:BB:CC:DD:EE:FF 6272...0003
        └──┬───┘ └──┬──┘ └─────┬──────┘
        parts[2]  parts[3]   parts[4]
          名称   ← 当成 MAC   ← 当成 UUID
```

登记结果：**名称只剩 `OPPO`，MAC 变成 `Reno9`，UUID 变成真实 MAC** —— 一条永远匹配不上的死记录。
而工具只打印「已发送添加钥匙命令」，**没有任何报错**。用户以为成功，到车边却不通电。

> 这也是「我方文档曾写『用 Qt 工具就不会打错』」这句话必须作废的原因：
> 工具只是省掉了手打 32 位 UUID，**名字这条路径它同样会错**。

**验收**（四条全过）：

1. 手发 `KEY ADD OPPO Reno9 AA:BB:CC:DD:EE:FF <32位uuid>` → **拒绝**并提示「名称不能包含空格」，`KEY LIST` 不变；
2. 手发 `KEY ADD 手机-03`（缺 MAC）→ 报「参数个数不对」+ 用法，`KEY LIST` 不变；
3. 工具内选一个名为 `OPPO Reno9` 的设备 → 命名框**预填 `OPPO-Reno9`**（空格已替换）→ 确认后 `KEY LIST` 名称正确、UUID = 扫描值；
4. 在命名框手动输入 `我的 手机`（带空格）→ **不发送任何命令**，就地报错。

**内存代价：0 常驻。** 个数校验是对已有 `parts` 做一次 `len()`；名称校验是一次 `" " in name` 判断。
都在原有解析路径内，不新增字段、不新增缓存、不新增字符串常量表。

## 十、我方现状与规避（仅说明，不需要对端配合）

| 现象 | 我方当前规避 |
|---|---|
| 名称含空格导致命令错位（第 19 条） | **默认无法规避**——手机广播名 = 系统蓝牙名（`OPPO Reno9` 这类出厂名带空格）。可选动作：详情页「设备名 → 按编号改名」会去空格并加后缀（`OPPOReno9-03`，改的是系统蓝牙名，需二次确认）；或以 `OPPO-Reno9-03` 之类的名字手工登记 |
| 同名覆盖（第 6 条） | 「按编号改名」后名称天然带 `-NN` 后缀，同型号手机不会同名；不改名时靠编号区分 UUID |
| `-` 占位覆盖（第 7 条） | 每次改钥匙严格执行 `KEY LIST` 留底 → `DEL` → `ADD` → 再 `KEY LIST` 对数 |
| UUID 格式（第 13 条） | 只用 Qt 工具传扫描值，禁用手打 |
| 上限 10 把（第 10 条） | 单车 ≤3 把，不触顶 |
| 名字可冒充（第 11 条） | 手机只靠 UUID；**但手环侧我方无法规避**——只能等对端改 |
| 阈值全局统一（第 17 条） | 手机侧发射功率已固定 `HIGH(+1dBm)`，客户端没有可调补偿；只能靠对端按钥匙设阈值 |
| 多设备显示错乱（第 18 条） | 我方无法影响对端显示逻辑；只能保证自己 250 ms 稳定广播，让判定尽量快 |

> 以上均为绕行，不是修复。第 6、7、11、19 条不实施时，多手机场景仍存在丢钥匙与误通电风险；
> 第 11 条未实施前，**同型号手环互通属于已知未修复漏洞**；第 19 条未实施前，
> **任何带空格出厂名的手机都有「看起来登记成功、实际永远不通电」的风险**。
