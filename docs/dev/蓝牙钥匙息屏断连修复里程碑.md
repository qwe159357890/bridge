# 蓝牙钥匙息屏断连修复里程碑（v0.3.009 → v0.3.012）

> **问题**：手机息屏一段时间后，ESP 接收端显示「钥匙不在」——收不到客户端的 iBeacon 广播；期间广播断断续续，最长静默近 100 秒并实锤一次真实误断电。
> **结局**：v0.3.012 一行档位改动根治——息屏广播从 LOW_POWER(1000ms) 提升为 BALANCED(250ms)，累计 2.6 小时息屏零断连；**ESP 接收端零改动**。
> **日期**：2026-11-19　**关联文档**：[ble-key-change-ledger.md](ble-key-change-ledger.md)（§2.10~2.13 为本次改前留档）、[release-pipeline.md](release-pipeline.md)

## 一、问题与排查历程（脉络：观测 → 定位 → 实验 → 根治）

| 脉络 | 版本 | 一句话 |
|---|---|---|
| 观测 | v0.3.008 | 50 项验收改「挂机跑 + 上传日志」，发现问题线索 |
| 深睡兜底 | v0.3.011 | 疑似深睡杀广播，加 10 分钟精确闹钟拉活（后被证明不是主因，但保留作兜底） |
| 实验根治 | v0.3.012 | 台架实测实锤 ROM 节流机制，息屏档位改 250ms，零断连 |

### 1.1 排查工具链（本次最大资产，可复用）

双侧日志 + 墙钟对齐 + 黑窗自动取证，全部纯只读：

1. **ESP 串口墙钟观测器**（Python，占用 COM8 前需先关掉 Qt 串口监视器）：逐行给 ESP 日志打墙钟时间戳（用「首行已连接时刻 − 首行 uptime」换算 ESP boot 时刻，此后 uptime + boot = 墙钟），自动识别**钥匙黑窗**（匹配=近 → 远/None → 恢复）并记录起止时长；
2. **黑窗快照助手**：轮询事件文件，黑窗进行中超过 20 秒时自动通过无线 adb 只读抓一次手机 `dumpsys bluetooth_manager`——用于排除「客户端会话死亡」（结论：亮屏/黑窗两态 dumpsys 完全相同，该 ROM 的 dumpsys 看不到广播注册状态，此路不通，判定只能靠 ESP 收包实况）；
3. **无线 adb**：USB 插入 → `adb tcpip 5555` → 拔线 → `adb connect 192.168.31.109:5555`。注意每次新 shell 会重启 adb daemon，需重新 connect；
4. **手机本地 logcat**：`adb logcat -d | grep BleKey` 比服务器环形缓冲（500 行）更全，但环形缓冲只保留约 6 分钟，要趁热抓。

### 1.2 机制实锤（1000ms 档基线，07:08~08:03，55 分钟息屏）

- **24 次黑窗**，每 1~4 分钟一轮；ON 相 30~110 秒 / OFF 相 5~**97.4 秒**；黑窗中偶发孤立单帧；
- **自恢复，与客户端 60 秒巡检重建无关**：07:39:45 在无任何重建动作时自愈；07:36:56 重建落在黑窗中也没提前恢复——**客户端重建救不了 ROM 节流**；
- 亮屏时段 **0** 黑窗；RSSI 全程 -63~-66 dBm 稳定（无射频问题）；
- 系统策略排查：deviceidle 白名单✓、省电模式关✓、appops 全允许✓，settings 里无 oplus 蓝牙节流开关——**节流在厂商 HAL 层，改不了，只能绕**。

### 1.3 两个高危实锤（用户判断「59.3 秒不是上限」完全正确）

1. **07:18 黑窗**断电计时跑到第 **59.3 秒**才被单帧取消——距误断电 1.6 秒；
2. **07:43 黑窗（97.4 秒）→ 07:45:08 实锤真实误断电**：`点火=待机 继电器=断开`，钥匙恢复后 07:45:29 自动重新吸合。台架无实际损失，真车上就是熄火风险。
3. **安全性确认**：ESP key_matcher 有 rssi_on/rssi_off 迟滞门，「人走断电」不受影响——走远后的偶发帧信号不够强，不会把匹配置回「近」，断电计时不会被重置。

### 1.4 深睡单独验证（结论：深睡无害）

手机 CPU 深睡（Doze）期间 **BLE 广播由蓝牙芯片自主完成，不依赖 CPU**：今晨 06:54~07:08 深睡窗口（App 日志停摆期）ESP 仍 135/189 行「匹配=近」。该窗口出现的 41 秒黑窗是 1000ms 档被 ROM 节流所致，**不是深睡造成**。v0.3.011 的 10 分钟闹钟兜底保留（防进程意外死亡），但不为此问题必要。

## 二、根因定论与修复

### 2.1 根因

**ColorOS 对 `ADVERTISE_MODE_LOW_POWER`（1000ms）广播做周期性启停节流**（厂商蓝牙省电策略，HAL 层，无法从设置关闭），息屏时表现为周期 ON/OFF 相交替，OFF 相最长 97.4 秒。**BALANCED（250ms）及更快的档被豁免，广播连续不断**。

### 2.2 v0.3.012 修复（一行实质改动）

| 文件 | 改动 |
|---|---|
| `blekey/BleKeyBroadcastService.kt`（SLOW 分支） | `ADVERTISE_MODE_LOW_POWER` → `ADVERTISE_MODE_BALANCED`，文案「后台保底（250ms）」 |
| `blekey/BleKeyRuntime.kt`、`BleKeyBroadcaster.kt` | 注释与 docstring 同步 |
| `app/build.gradle.kts` | versionCode 3012 / versionName 0.3.012 |

FAST 与 SLOW 现共用 BALANCED：FAST↔SLOW 切换因幂等键相同不再重启会话（仅文案/状态更新），行为等价。发布链全程 aapt 验证 + gh-proxy 下载铁律，部署 mbh（sha256 `8EC772AF…`）。

### 2.3 验证数据（决定性对比）

| 阶段 | 档位 | 息屏时长 | 黑窗 | 最长静默 |
|---|---|---|---|---|
| 基线 | 1000ms | 55 分钟 | **24 次** | 97.4 秒（误断电 1 次） |
| 实验 | 250ms | 40 分钟 | **0** | ≤2.0 秒 |
| soak | 250ms | 98 分钟 | **0** | ≤3.29 秒 |

**soak 统计（1866 条状态行）**：
- 信号强度：均值 **-60.9 dBm**、中位 -61.0、P90 -57.0（峰值 -53 最强；-98 为偶发瞬时干扰单帧，判定用帧流不受影响）；
- 帧间隔：均值 **0.61 秒**、中位 0.46、P90 1.41、P99 2.09、最大 3.29 秒；
- 分布：<0.5 秒占 53.75%、0.5~1 秒 24.71%、1~2 秒 20.20%、2~3 秒 1.29%、3~5 秒仅 1 帧（0.05%）、**5 秒以上 0 帧**——对 ESP 的 10 秒降档线、60 秒断电门有巨大安全余量；
- 「远/None」状态行 = **0**。

## 三、关键经验沉淀

1. **ColorOS 只对 LOW_POWER(1000ms) 广播做周期性启停节流，250ms 及更快档豁免**——息屏断连的唯一根因；任何「更勤快重建」都救不了 ROM 节流，唯一解法是换档。
2. **BLE 广播由芯片自主完成，深睡（Doze）不停播**——App 日志停摆 ≠ 广播停止，判定客户端侧问题必须以对端（ESP）收包实况为准。
3. **该 ROM 的 dumpsys 看不到广播注册状态**（`0 BLE apps registered` 亮屏/黑窗两态相同无判别力），bt 栈日志被精简——判「谁停的广播」只能靠对端观测，别在 dumpsys 上耗时间。
4. **串口观测必须打墙钟时间戳**：ESP 日志只有 uptime，用「首行时刻 − 首行 uptime」推 boot 时刻后可全程对齐手机侧日志，双侧交叉验证才能定位「黑窗起点与重建无因果」这类关系。
5. **断电门（60 秒无帧断电）对「在场但被节流」无免疫**：本例差 1.6 秒实锤 + 97.4 秒真实误断电。本次靠换档根治未动 ESP；若未来再遇长静默场景，备选方案是 ESP 侧「只在 RSSI 衰减到远档后才启动断电计时」（key_matcher 已有 rssi_on/rssi_off 迟滞门，参数可远程下发）。
6. **排查临时工具可一次性搭建**：串口墙钟观测器 + 黑窗检测 + 自动快照 + 定期汇报循环，全部纯只读、复用 KeepAlive 的 goAsync/gs 模式思路；方法在本文档，工具按需重建。
