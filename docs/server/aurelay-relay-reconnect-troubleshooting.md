# 音频中继「切网络后不自动重连」根因排查报告

> 排查日期：2026-10-29（晚上，多轮持续排查）
> 结论版本：v1
> 涉及端：手机 App（appClient，Android）、PC 发送方（化合机器 pc-client，Python）、中心服务器（center-server，Ubuntu 86.74.128.24）
> 关联文档：`docs/server/aurelay-relay-troubleshooting.md`（同链路另一问题「正在接收但无声」）

---

## 一、背景与结论摘要

### 网络拓扑（先厘清，避免误判）

```
PC 发送方(化合机器 86.74.128.99, vnt组网)
   │ 主动出站 ws://039039.xyz:15151/api/aurelay/relay
   ▼
中心服务器(Ubuntu 86.74.128.24, vnt虚拟地址, 非公网)  ← 撮合房间 {S:PC, R:手机}
   ▲
   │ 魔百盒 192.168.31.30 公网 122.6.190.161 经 nftables 把 15151 转发到 86.74.128.24
   │ 主动出站 ws://039039.xyz:15151（DNS→公网→魔百盒→服务器）
手机接收方(OnePlus LE2120, device_id=f2c38ebee251a196)
```

- 手机在蜂窝/弱网下无公网入站能力，**两端都主动出站**连中心服务器，服务器撮合「S(PC)+R(手机)」到齐才发 `ready`。
- Bridge 主服务(15160) 在开发机本地 86.74.128.226(vnt)，与中转(aurelay 15151)是两套东西，**排查时别混**。

### 结论（一句话）

「切网络后不重连」经历了**三层递进**的根因，最终由 v0.1.86 根治：

1. **v0.1.84 之前**：手机端「切网瞬间三路网络回调并发 forceReconnect」竞态，留下「TCP 已连但 hello 未送达服务器」的**半死连接**，且手机端 watchdog 只看 `webSocket != null` 误判「已连上」，导致永久卡死。
2. **v0.1.85**：加了 generation 递增 + 500ms 防抖，但**没解决半死连接的判死**——判死本该由 pingLoop 心跳兜底，但 pingLoop 判死在实战中**从未触发过**（次级悬案），于是仍卡死。
3. **v0.1.86**：把「等 ready 超时判死」下沉到**常驻 watchdog 线程**（不再依赖失效的 pingLoop），半死连接最多 10 秒即被强制重连，**彻底根治**，用户实测「一分钟内都能自动重连」。

**遗留（未解决，已接受）**：
- pingLoop 心跳判死为何从未触发 → 悬案，但不影响自愈（watchdog 已独立兜底）。
- PC 端「提速尝试」（缩短握手超时 + 退避序列）触发**推流线程卡死** → 已回退，待后续抓线程栈定位。

## 二、三个阶段的完整证据链

### 阶段一：手机端半死连接（v0.1.84 部署后仍失败）

三方日志（手机上传→本机 MySQL `device_logs`、PC `86.74.128.99:8899`、SSH center_server）：

| 时间 | 手机端 | 服务器端 | PC 端 |
|---|---|---|---|
| 22:07:45 | 切网，三路回调并发 forceReconnect | — | 收到 409 断开 |
| 22:07:53 | 第4次重连 → **「已连上中转服务器」会话#3** | ❌ 无「接收方已接入」 | 连上 |
| 22:07:53 之后 | **日志永久停在「已连上」，再无 ready** | 只有 PC 反复「接入→下线」 | 反复「握手未就绪」重试 |

**核心矛盾**：手机 `onOpen` 触发（本地 TCP 三次握手在旧路由上「完成」），但 hello 没送达服务器，服务器从未登记手机。手机却以为连上了。

**三道兜底全失效的原因**：
1. watchdog 重连：判断「已连上」唯一依据是 `webSocket != null`，半死连接的 webSocket 已非 null → 空转不重连。
2. pingLoop 心跳判死：理论上 60 秒该触发，但日志里 **0 条「心跳超时判死」记录，连「发送心跳失败」都没有** → pingLoop 线程疑似失效（未定位）。
3. 切网回调触发点：22:07:45 那波已消费，之后无新网络事件。

### 阶段二：v0.1.86 判死下沉到 watchdog（根治）

`RelayClient.kt` watchdog 空转分支新增两类判死：
- **未就绪超时**：`onOpen` 后 10 秒(`READY_TIMEOUT_MS`)没收到 ready → 半死连接 → forceReconnect。
- **就绪后失联**：ready 后 60 秒没收到任何数据 → forceReconnect。

配套字段：`ready` 标志 + `lastOpenAt` 时间戳，在 onOpen/收到ready/forceReconnect/断线各处置位与重置。

**验证铁证**（手机日志 22:32:00）：
```
22:32:00  W 中继  已连上但 10295ms 未收到 ready（半死连接），强制重连
22:32:30  I 中继  收到 ready，中转链路就绪   ← 自愈成功
```
这正是 v0.1.85 会永久卡死的场景，被成功自愈。

### 阶段三：PC 端提速尝试 → 推流线程卡死 → 回退

用户要求「压缩重连节奏」，改了两处（PC 端 `constants.py` + `core.py`）：
- `CONNECT_TIMEOUT_S` 8.0 → 4.0
- `_RECONNECT_BACKOFF` (3,5,10,15,20,30) → (1,2,5,10,15,20)

**结果**：切网后 PC 推流线程在 22:46:13 后**日志停更（进程还活着，HTTP 8899 正常响应 200）**，服务器 22:47:57 清 PC 后 PC 再没回来，手机陷入「接入→等ready→半死判死→重连」死循环。

**卡死前兆**：日志反复「⚠ 输出队列满，丢弃 1 帧——推流线程已 17ms→77ms→78ms 未取帧」，stall_ms 逐步涨到停滞。

**判断**：改快放大了代码注释里早已警告的并发竞速隐患（`RelaySender.connect()` 慢阻塞 + 409 短退避，高频重连时「新 S 顶旧 S、自己踩自己」），可能触发线程死锁/资源耗尽。**但不排除独立偶发卡死**（日志「CPU 被抢占」提示那台机器当时可能恰好遇到杀毒/CPU 抢占）。

**处理**：完全回退两个值，恢复稳定。

## 三、遗留问题与后续建议

1. **pingLoop 判死悬案**：下次若需定位，在 `RelayClient.kt` pingLoop 循环头加 `DiagLog.d` 打点，确认线程是否存活、循环是否在跑。
2. **PC 端中转重连并发竞速**：要「又快又稳」的正确方向不是调数字，而是给 `RelaySender.connect()` 加重入保护（同一时刻只允许一个连接尝试在跑），从根上消除「新 S 顶旧 S」。定位卡死可用 `py-spy dump --pid <pid>` 抓线程栈。
3. **经验教训**：重连/超时类参数**不要单点压快**——退避序列的「递增封顶」结构是防「两端稳定到齐」被高频自踩的关键，改动会连锁影响服务器 close 竞态与房间撮合。
