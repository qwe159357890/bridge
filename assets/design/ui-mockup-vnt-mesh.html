集成 VNT（方案 A：JNI 内嵌）— 主页新增第 5 个 Tab「组网」
方案 Alibvnt_jni.so 内嵌 服务端零改动前台服务 specialUse
本版要点：
① 主页 Tab 增加「组网」 —— 排在「快递扫码」之后（页面 id = 4），与既有 4 个 Tab 同一套顺序/改名机制。
② 生命周期是「显式开关 + 前台服务常驻」，不是 ESP32/销售那种「进页面才连、离开即断」；切 Tab、退后台都不断连。
③ 首次连接要过系统 VPN 授权框（Android 同时只允许一个 VPN，会挤掉其它 VPN App，需明确提示）。
后端对接硬约束：VNT 侧服务端零改动；Bridge 服务端不动。客户端严格复用官方 com.vnt.* 绑定（包名不可改，JNI 符号硬绑定），仅自建 VntVpnService 与 Compose 页面。路由只加虚拟网段 + 出口网段，绝不加 0.0.0.0/0。

设计要点与待确认项：
  • 页面 id = 4「组网」：TabOrderPrefs 的 PAGE_TITLES/PAGE_ICONS 各加一项，并把硬编码的 isValid()（size==4、集合 0..3）改为 5 项；必须做旧值迁移，否则老用户已存的 0,1,2,3 会判非法静默回退默认顺序、自定义排序与改名丢失。
  • 生命周期刻意不同于 ESP32/销售：那两条是「进页面才连、离开即断」（省电优先，页面少用）；组网是基础设施，走 VntVpnService 常驻 + 显式「开始/停止」按钮，切 Tab 与退后台都不断开，页面只订阅状态。
  • 前台服务 Android 14+ 四件套：FOREGROUND_SERVICE + FOREGROUND_SERVICE_SPECIAL_USE + foregroundServiceType="specialUse" + PROPERTY_SPECIAL_USE_FGS_SUBTYPE，另需 BIND_VPN_SERVICE 权限与 android.net.VpnService 的 intent-filter；接入前逐条对照 docs/dev/crash-ledger.md §5。
  • 路由红线：只加虚拟网段与服务端下发的出口网段，绝不加 0.0.0.0/0——否则 Bridge 自身的主 WS、微信、销售长连接全被卷进隧道，表现为「一开组网什么都连不上」。
  • 包名不可改：com.vnt.* 官方绑定原样拷入，JNI 符号（Java_com_vnt_VntManager_nativeInit 等）与类名一一对应；改包名需同步改 Rust 侧 #[no_mangle] 符号名。
  • 产物来源（P0 已完成，本地零安装）：libvnt_jni.so 直接用官方 vnt-dev/vnt tag v2.0.11 发布的预编译产物（5,042,792 B，SHA256 c33535b1…8f48），版本与本地 references/vnt 源码 2.0.11 一致。已入库 app/src/main/jniLibs/arm64-v8a/；tools/vnt/verify_so.py 纯 Python 校验 SHA256 / ELF64-AArch64 / 4 段 16KB 对齐 / 23 个 native 声明与 23 个导出符号零缺失，全 PASS。不需要安装 Rust 或 NDK。
  • nextEvent 是阻塞调用：必须在独立 daemon 线程跑变更循环，停止时用「取消标志 + generation 校验」双保险，否则线程卡死导致服务退不出。
  • 设备 ID：默认用 Bridge 已有的 ANDROID_ID 显式写入 setDeviceId（VNT 在 Android 上不取机器码，避免同网内撞 ID）。
  • 状态刷新节奏（已拍板）：只有「App 在前台 + 停在组网页」才刷——进入页面立即刷一次（不等第一个周期），之后每 5 秒一次；离开页面 / 退后台 / 锁屏立即取消定时任务，一次都不再拉。用 Compose DisposableEffect 判定（切到别的 Tab 就移出组合），比 VntApp 的 Activity 生命周期置位更精确。关键：getClientList() 不是读内存，它会向服务端发一次 RPC（send_to_gateway_expired + 等响应最多 3 秒阻塞），必须在后台单线程调并加 generation 校验；每轮只有它发网络包，getServerList/getRouteTable/getNatInfo/getNetwork 都是本地读取。
  • 三项数值的真实出处：P2P = 路由 metric==1；↑12K ↓84K = 本机两次采样差分算出来的（底层只有累计字节数，没有速率字段，页面隐藏再回来必须重置采样基准否则出现虚假尖峰）；18 ms = 有 P2P 路由时的真实往返，中继行的 ≈46 ms 是 服务端RTT×2 的估算值，UI 用 ≈ 区分。
  • 设备上下线没有事件：服务端确实会主动推 PushClientIps，但 JNI 层 RuntimeEvent 只有 InstanceStopped / Changed(config) 两种，推不到 Java ⇒ UI 只能靠轮询看到变化（滞后 ≤1 个周期，后台不刷新）。要做掉线通知需自己在状态层做前后快照差分 + 连续 N 周期防抖（P2）。
  • 心跳台账：VNT 自身保活在 Rust 内部、周期不可从 Java 侧调，须作为「黑盒常驻连接」补登记进 docs/dev/heartbeat-inventory.md §1。
